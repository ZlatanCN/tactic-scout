## Problem Statement

TactiScout 的招募案件已经使用 LangGraph 组织多轮调查，但随着上下文模式、工具协议、追问恢复、失败处理和用户偏好不断加入，运行时职责逐渐分散在节点工厂、手写调度、应用层计时与恢复逻辑中。结果是同一事实可能从多份上下文重复重建，节点失败缺少统一语义，运行审计只能依赖临时日志，跨案件偏好也没有与案件 checkpoint 明确分开。

用户需要的是一个调查过程可恢复、可解释、可停止、信息不足时能继续追问，并能把较长调查稳定带到结论的球探 Agent。维护者需要的是一套足够小的运行时边界：业务规则仍由代码负责，LangGraph 负责状态、路由、工具循环、暂停恢复、持久化、重试、超时和流式事件，而不是继续手写这些通用机制。

## Solution

保留现有的招募案件领域 `StateGraph`，逐步收口到 LangGraph 原生运行时能力：

- 通过 `contextSchema` 和 `Runtime.context` 注入 repository、planner、知识库、观察器及实验配置，使运行时依赖不进入 checkpoint。
- 每个 Planner 回合只读取代码确定性生成的 `DecisionSnapshot`；最新用户明确要求始终高于历史对话和长期偏好。
- 继续使用原生 `ToolNode`、`bindTools`、`toolsCondition`、`interrupt()` 和 `Command(resume)`。
- 为有外部 I/O 的节点配置节点级 `timeout`、类型化 `retryPolicy` 和 `errorHandler`；用户回合使用 `durability: "sync"`，让可恢复状态在副作用前得到持久化。
- 通过脱敏的 `inspectCaseRun()` 暴露 `getStateHistory()` 审计结果，帮助定位失败、重试、暂停和恢复发生在哪个阶段。
- 用 `BaseStore` 保存用户显式批准、可查看和可删除的跨案件长期偏好；案件事实、候选、报告和临时条件继续留在 checkpoint 与业务数据中。
- 只有在同一完整图、冻结数据和交错配对实验中证明有收益的并行 enrichment、`Send`、候选评估子图或局部 `createAgent` 才进入默认链路。未通过的实验路径在迁移完成后删除。

目标不是让每个节点都调用一个 LangGraph API，而是让每种框架能力承担它真正擅长的职责，并保持确定性业务规则可验证。

## Implementation Decisions

### 交付边界与既有决策

- 本规格延续 ADR-0005、ADR-0010 与 ADR-0014，不替代受约束调查阶段、招募案件 `StateGraph` 或模块化单体。
- `createRecruitmentConversation()` 继续作为领域图工厂。外部信号和历史档案 enrichment 使用经配对验证的 LangGraph `Send` fan-out；候选评估不使用 `Send`，Planner 循环继续走显式 Planner→`ToolNode`。
- 工作按独立切片推进：运行时上下文；图拆分与 `DecisionSnapshot`；原生节点策略与同步持久化；脱敏 checkpoint 审计；并行 enrichment；持久化匿名偏好 Store；最后再评估条件并发与高阶 Agent 实验。每个切片必须先保持已有公开行为，再进入下一项。

### 运行时上下文

- 定义 `RecruitmentRuntimeContextSchema`，承载可序列化的执行配置与类型化服务依赖。
- 用当前的构造形式编译现有领域图：

```ts
new StateGraph({
  state: RecruitmentState,
  context: RecruitmentRuntimeContextSchema,
})
```

- 运行时上下文包含球员仓库、Planner、需求解释器、知识库、参考名称解析器、球队名单补充、证据评估器、跟踪观察器、已配置的 enrichment 客户端和当前浏览器明确批准的偏好。实验开关不进入正常运行时。
- 节点从第二个参数中的 `runtime.context` 读取依赖，不再闭包持有同一依赖的副本。
- `RecruitmentState` 只保存 checkpoint、恢复、证据、报告和安全失败恢复所需的可序列化案件事实。函数、客户端、观察器、完整异常、模型隐藏推理和原始供应商响应不进入状态。
- 同一张已编译图在测试中可以用不同运行时上下文调用。缺少必需依赖时，必须在任何仓库、Planner 或供应商请求之前失败。
- 环境读取与已配置客户端构造留在应用组合边界。供应商适配器继续拥有自己的传输和来源能力。
- 用户取消继续使用 `AbortSignal` 穿过图和工具。`RunControl` 只用于本地服务在 superstep 边界优雅排空，不替代用户取消。

### 图职责与 DecisionSnapshot

- 把当前较大的规划职责拆成显式阶段：

```text
START
  → record_user_turn
  → understand_request
  → update_case_facts
  → prepare_decision_snapshot
  → policy_gate
      ├─ deterministic action → validate_action
      ├─ needs Planner      → plan_next_action → validate_action
      └─ terminal           → review_recommendation

validate_action
  ├─ tool                 → execute_tool
  ├─ ask                  → wait_for_user
  ├─ review               → review_recommendation
  └─ replan               → plan_next_action

execute_tool
  → update_case_facts

review_recommendation
  ├─ retry                → prepare_decision_snapshot
  ├─ optional enrichment  → deliver_recommendation
  └─ deliver              → deliver_recommendation

deliver_recommendation
  → END
```

- `update_case_facts` 一次性把工具观察吸收为类型化案件事实，单个工具不再各自解释候选、游标、预算和证据状态。
- `prepare_decision_snapshot` 确定性构造 Planner 的唯一权威视图，包括最新确认需求和硬条件、合格候选与被排除身份、带单位和样本边界的已观察证据、准确分页游标、剩余工具预算、待回答问题上下文、报告范围和来源能力限制。
- `policy_gate` 与 `validate_action` 包含确定性策略、资格、阶段、游标、预算、重复动作、追问和复核路由规则。
- `plan_next_action` 只在已校验阶段和快照允许的动作中选择。它只读取 `DecisionSnapshot`；历史消息仍可用于引用和审计，但不用于重新解释硬事实。
- 最新明确用户要求高于先前对话和存储偏好。Store 值只在用户批准且该字段确实遗漏时补充长期偏好，绝不提供案件事实、候选、报告、临时条件或推断画像。
- 状态只保存 DecisionSnapshot 版本、安全摘要或哈希和审计所需统计，不保存可能漂移的第二份完整事实副本。
- 同时更新状态并选择下一节点的节点使用 `Command`；普通固定跳转仍使用边。

### 原生工具、中断与图事件

- `bindTools()` 只暴露当前阶段合法的具名工具。数据动作由原生 `ToolNode` 执行，`toolsCondition` 选择原生工具路径。
- 追问和结束等控制动作由领域图路由，不加入模仿工具循环的自定义机制。
- 现有结构化位置与球员身份问题继续使用 `interrupt()`，并通过 `Command` 恢复；沿用同一案件 thread。
- `ToolNode` 将业务可恢复错误保留在类型化状态合同中。未知运行时失败交给节点策略，不能伪装成零结果工具观察。
- 现有传输层继续负责模型限流与协议修正。图 `retryPolicy` 只处理传输层尚未处理的有类型幂等读取失败。
- v3 `streamEvents` 与类型化自定义 `StreamChannel` 继续作为进度和候选事件来源。界面只收到应用 DTO，不接触图状态、提示词、隐藏推理或原始供应商数据。
- 长节点只使用真实的图阶段更新。它不得通过定时心跳伪造百分比。

### 节点策略、持久化与恢复

- 每个节点从中央表声明一项策略：超时、重试、错误处理和恢复目标。
- Planner、工具、上下文摘要和外部 enrichment 沿用现有模型或供应商预算设置时限。图超时是节点总时限的兜底，不能与相同截止时间的传输超时竞速。
- `errorHandler` 写回类型化脱敏失败摘要，并返回遵循阶段恢复策略的 `Command`。它不能把堆栈、提示词、token、原始供应商响应或隐藏推理写入案件状态。
- `retryPolicy` 可以在有类型的瞬时网络或供应商失败后重试幂等读取。它不得重试评估、变更、候选预算递增或已经写入状态的操作。
- 可选 enrichment 失败时要明确记录覆盖不可用，并继续生成核心报告。核心证据、身份、预算、候选策略和 Reviewer 失败不能转换成成功空结果。
- 用户回合使用 `durability: "sync"`，使对用户可见的副作用之前所需状态和中断可恢复。应用仍负责请求 ID、容量限制和同案队列语义。
- `RunControl` 用于优雅排空服务：停止接收新回合，让活动图到达 checkpoint 边界，关闭 Store，再在重启后恢复。

### DecisionSnapshot 结构形状

以下原型推导出的形状用于表达合同。最终字段名可以沿用现有领域类型，但语义必须保持稳定。

```ts
type DecisionSnapshot = {
  version: 1;
  case: {
    latestUserRequest: string;
    brief: RecruitmentBrief;
    confirmedPositions: SelectablePosition[];
    pendingQuestion: PendingQuestion | null;
  };
  caps: {
    stage: InvestigationStage;
    allowedActions: RecruitmentActionName[];
  };
  candidates: {
    eligibleIdentityGroups: CandidateIdentityGroupReference[];
    evaluatedPlayerIds: string[];
    excludedIdentityIds: string[];
  };
  evidence: CandidateEvidenceDirectory;
  search: {
    onDemandMetricGroups: CapabilityMetricKey[];
    discoveryScope: {
      strategy: DiscoveryStrategy;
      metricGroups: CapabilityMetricKey[][];
    } | null;
    exactNextOffset: number | null;
  };
  budget: ToolUseCounts;
  sourceLimits: SourceCapabilitySummary;
};
```

- 快照每回合从代码拥有的规范状态重新生成，不作为可变事实源写回。
- Planner 输出在到达 `validate_action` 前必须经过 schema 校验。
- 只有现有受约束策略明确指出安全时，确定性动作才能绕过 Planner。确定性策略动作与 Planner 动作都写入决策轨迹。

### 脱敏案件运行审计

- 新增 `inspectCaseRun({ threadId, limit })` 作为最高层审计 seam，由已编译图的 `getStateHistory()` 支撑，只返回白名单字段。

```ts
type CaseRunInspection = {
  checkpoints: Array<{
    checkpointId: string;
    step: number;
    nextNodes: string[];
    interrupted: boolean;
    safeSummary: {
      action?: string;
      stage?: string;
      candidateCount?: number;
      evaluatedCount?: number;
      failureKind?: string;
    };
  }>;
};
```

- 适配器不能返回完整 checkpoint 值、提示词、原始球员记录、供应商载荷、异常、模型推理或凭据。
- 同一审计 DTO 可以由评测 CLI 使用；只有现有产品路径确需时，才增加内部诊断路由。本切片不增加公开审计界面。

### 并行 enrichment 与条件并发

- 外部信号与历史档案 enrichment 是默认并行的唯一候选，因为二者的输入和状态写入彼此独立。每个分支拥有独立策略和覆盖失败语义。
- 只有冻结或重放外部响应、核心候选顺序与报告证据和串行一致、配对运行显示可复现延迟收益时，才采用并行。路径、耗时和覆盖元数据可以不同。
- 只有每个候选任务独立、结果 reducer 确定、共享工具预算不会并发递增、供应商并发限制得到执行时，才评估 `Send` 候选评估。
- 如果 `Send` 通过，单个候选评估可以成为拥有明确输入输出合同的子图，不能原样嵌入整个招募状态。
- 只有以窄工具集作为局部内循环，并证明正确性一致且有可测成本或维护收益时，才评估 `createAgent` 替代现有 Planner 到 `ToolNode` 循环。
- 配对决策后删除每个失败分支及实验专用开关。最终图中不能保留不可达调度器、节点或备用上下文路径。

### 跨案件匿名偏好

- 浏览器生成匿名 `memoryOwnerId`，并把它作为本地应用读取偏好 Store 的身份。此机制用于原型隔离，不是认证。
- Store namespace 为 `["users", memoryOwnerId, "preferences"]`。
- 每条偏好包含偏好键、面向用户的值、来源、最后确认时间和安全说明其适用时机的文字。
- Store 接口使用 LangGraph `BaseStore`。本地原型由 SQLite 持久化，`InMemoryStore` 只用于测试，未来生产环境计划替换为 PostgreSQL。
- 用户可以列出、编辑、删除单条偏好，也可以清空所属匿名身份的全部偏好。
- 偏好只在用户明确操作或批准后保存。偏好不能包含案件事实、候选、报告、临时条件、搜索观察、模型输出或推断人格。
- 每个案件都以当前请求为起点。Store 值只在字段遗漏时注入，当前案件中的明确请求始终优先。
- 本地应用默认关闭时同时关闭 checkpoint saver 与偏好 Store。删除偏好或本地浏览器身份只影响对应匿名 namespace。

### 上下文管理收口与实验门槛

- 正常运行时唯一使用 `projection`：从案件规范状态构造单份 `DecisionSnapshot`，不额外摘要整段案件历史，也不提供旧版、evidence reread 或上下文模式开关。
- 已完成的完整图配对评测中，`projection` 和 `unified` 均通过五组硬门槛并完成压力补答；p50/p95 分别为 203020/244654ms 与 279913/295157ms，Planner 请求分别为 123/195，可用输入 token 分别为 4232909/7435525。以通过硬门槛后的延迟、请求和可用 token 作为选择依据，采用 projection。
- 实验只用于选择机制，不证明逐项输出等价：通过硬门槛的两个臂候选顺序并非每组相同。其余历史臂 legacy/evidence/summarized 分别通过 3/5、2/5、4/5；summarized 只有 4/5 运行实际接受已验证摘要，未通过门槛。evidence 臂 token 遥测不完整并保持未知，不估算。完整记录见 issue 06 引用的结果文件。
- 配对实验已在同一完整图、模型、冻结数据、补答脚本和重复预算下结束。旧模式、比较开关与专用测试已删除；当前架构只运行 projection。
- 硬门槛为：报告完成；最新条件覆盖正确；中断恢复连续；候选与证据引用保留；无重复工具副作用；不暴露被拒绝身份或隐藏提示数据。
- 所有实验臂通过硬门槛后，才按报告证据质量、p50/p95 延迟、模型 token 用量、工具调用和维护复杂度选择赢家。
- 赢家成为默认图行为。迁移后删除其他模式、开关及其实验专用测试。

### 实验验收规则

- 每项机制变化都与对照臂配对使用同一张已编译图、快照、模型、可用的随机种子和冻结数据，并交错执行顺序以减少供应商漂移。
- 正确性是闸门，不能与速度交换。更快但结果错误、为空、重复或只得到部分证据支持的实验臂直接失败。
- 报告通过率、失败检查名、候选人数、证据引用一致性、报告完成、p50/p95 延迟、Planner 请求数、工具数和可用 token 用量覆盖。
- 缺失或部分 token 遥测保持未知，不能从文本长度估算。
- 只有收益可复现，且不会增加未说明的静默降级或过度维护复杂度时，才采用该机制。

### 公开交互合同

- 对话响应继续暴露 `needs_input`、完成、失败、取消、brief、报告、安全重试消息，以及类型化位置或球员身份问题。
- HTTP/SSE 每回合保留一个 request ID，将取消传到仓库与工具，只发送有界的进度或候选事件，并在取消后释放同案队列。
- 缺少必需模型或运行时依赖属于服务或配置失败，绝不能作为零候选结果。
- 面向用户的审计只说明运行到哪一阶段、什么安全失败，不宣称置信度、完成百分比、隐藏推理或推荐真值。

## Testing Decisions

本项目中的良好测试应验证公开产品边界和可观察行为，避免断言私有节点函数、LangGraph 内部实现细节、精确生成文案或非必要模型输出顺序。当完整图不是验证同一行为的最佳位置时，确定性领域规则可以使用纯函数测试。

### 复用四个现有或最高层 seam

1. **完整招募对话**
   - 使用 `createRecruitmentConversation().turn()` 验证多轮行为、当前条件覆盖、原生工具、中断恢复、Reviewer 路由、快照等价、超时、重试、失败恢复、取消、偏好优先级和最终报告合同。
   - 先例：现有招募交互、身份、替代者、证据、取消、上下文和 LangGraph 原生工具调用测试。

2. **应用 HTTP/SSE**
   - 使用 `createApp()` 验证回合请求、待补答响应、类型化位置与身份输入、进度/候选/错误事件顺序、取消、同案队列释放、缺失上下文失败，以及新增审计路由时的脱敏输出。
   - 先例：招募 HTTP 与进度/SSE 测试。

3. **配对完整图评测**
   - 使用现有 `pnpm eval:local-agent` Harness 比较机制。实验臂只通过显式 CLI 开关增加，除被改变因素外保持行为一致。
   - 先例：LangGraph 原生工具协议、上下文管理、搜索新鲜度、证据评估器、比较、方法复用与历史档案消融。

4. **脱敏案件运行审计**
   - 使用 `inspectCaseRun()` 验证 checkpoint 步骤顺序、中断、安全失败类别、计数、活动下一节点、脱敏和恢复前后连续性。
   - 这是唯一新增 seam，因为 checkpoint 历史的安全和顺序无法通过最终报告充分观察。

当上述四个 seam 足以证明可观察行为时，不应为节点超时、`errorHandler`、`retryPolicy` 或 `getStateHistory()` 新增内部节点测试 seam。

### 按迁移切片的行为测试

- 运行时上下文：同一张已编译图在测试中用两个不同上下文运行；缺失必需上下文在任何外部调用前失败；运行时函数不出现在 checkpoint 状态中。
- 图拆分与 DecisionSnapshot：在修改和撤销年龄限制、多页搜索、报告追问、参考球员替代、身份歧义和最新位置选择中，通过完整图比较旧组装上下文与快照输入。每项的合法动作和最终证据必须一致，快照字段必须与 checkpoint 中的案件事实相符。
- 原生节点策略：注入有类型的瞬时读取失败、不可重试失败、超时和可选 enrichment 失败。验证重试计数不会重复预算或状态写入，核心报告交付符合规定，安全失败类别被记录且不夹带原始错误数据。
- 同步持久化：使用已配置 SQLite checkpointer 运行到一次追问中断，重启对话边界，以同一 thread 恢复，并验证只出现一个待回答问题和一份报告。
- 审计：检查正常运行、中断、恢复运行、可重试失败和最终失败。验证步骤单调、中断与下一节点标记正确、摘要符合白名单，且没有秘密或原始证据。
- 并行 enrichment：使用串行与并行臂的冻结响应，验证核心报告等价和证据引用身份一致；在配对评测中比较延迟和失败覆盖。单分支失败必须保留覆盖不可用，并仍交付核心报告。
- 偏好 Store：使用临时 SQLite 文件验证重建后持续、不同浏览器 namespace 隔离、列出/编辑/删除/清空、当前请求优先以及不含案件事实。`InMemoryStore` 只用于缩短纯合同测试。
- 上下文模式选择：已通过完整图配对评测采用 projection；迁移后检索应确认旧版、evidence reread、summary、模式开关及专用死代码均已删除。
- `Send`、子图或局部 `createAgent`：只在更早切片通过后运行。验证与串行或 Planner 到 `ToolNode` 行为语义等价、并发限制、重复抑制、错误覆盖及可测配对结果。被拒绝分支必须删除，不能只留下禁用开关。

### 宣告迁移完成前必须验证

- 现有完整测试套件和 Web 构建通过。
- 使用已配置供应商或确定性 Planner 的可运行本地对话，能从自然语言请求经过追问、候选证据和 Reviewer 完成代表性案件报告。
- `pnpm eval:local-agent` 为每个采用或拒绝的条件机制生成配对证据。
- 本地手动运行确认 HTTP/SSE 进度、取消、恢复和报告渲染使用同一套公开 DTO。
- 最终代码检索确认正常组合中不存在失败上下文模式、重复工具调度器或仅实验可达的分支。

## Out of Scope

- 不迁移、不解释本次运行时迁移之前生成的 checkpoint。当前本地原型可以清理旧案件 checkpoint；浏览器保存的招募计划与用户可见报告快照仍独立处理。
- 不做多实例部署、分布式锁、横向 checkpoint 协调、认证、账号身份或匿名偏好 Store 的生产级授权。
- 不在本阶段实现生产 PostgreSQL Store。设计方案只要求未来可以在 `BaseStore` 后替换 SQLite。
- 不做实时协作、团队共享记忆、跨用户聚合画像或浏览器计划云同步。
- 不把 Store 偏好当作案件事实、身份证明、转会资格或来源证据。
- 不把招募 `StateGraph` 替换成通用 ReAct Agent 或单次 LLM 调用。
- 不对实时 Planner、候选搜索、候选评估、报告检索或报告生成使用 `cachePolicy`。
- 不在本阶段增加 checkpoint 审计新界面。
- 不从工作流测试或配对机制结果宣称短名单质量、推荐准确率或框架普适优越性。
- 不为假设中的未来用途长期保留实验开关、失败分支或旧运行时实现。
- 不改写供应商访问、许可、身份、候选资格、证据合同、报告 DTO 语义或受约束调查阶段，除非新运行时互操作确有必要。

## Further Notes

- 当前安装的 LangGraph 栈能够提供目标 API，但实施前必须对照已安装版本确认准确签名。特别地，图构造使用带 `context` 的构造形式，节点运行时策略属于节点注册参数。
- 最初的主要热点是规划节点，它同时承担 Planner 输入组装、合法动作推导、策略选择和状态路由。后续机制加入前，应先按行为不变原则拆分它。
- projection 直接从规范案件状态生成单份权威 Planner 决策视图；上下文与来源证据保持在案件状态和相应工具结果中，不创建第二份可漂移的长摘要。
- 现有测试已经覆盖图、HTTP/SSE、上下文、取消和多项消融。测试面广是保留现成 seam 并小步迁移的理由，不是增加更多内部 seam 的理由。
- 作为本地原型，SQLite 持久化与匿名浏览器身份是有意选择。规格不得把它们描述为生产安全或多用户保证。
- 只有实施确立了超出 ADR-0005、ADR-0010 与 ADR-0014 的长期横切决策时，才需要新 ADR。本规格当前就是可执行的设计记录。
