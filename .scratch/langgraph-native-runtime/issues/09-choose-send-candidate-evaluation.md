# 09: 决定 `Send` 候选评估去留

**What to build:** 用配对实验比较现有串行候选评估与 LangGraph 原生 `Send` 并发路径。只有候选结果、证据引用和报告等价，预算与供应商并发限制安全，且并发带来可测收益时才保留；否则连同实验开关一起删除。

**Blocked by:** 04, 06

**Status:** resolved

**Labels:** ready-for-agent

- [x] `Send` 实验只处理彼此独立的候选评估任务，并由确定性 reducer 合并结果。
- [x] 共享工具预算不会因并发发生丢失更新，供应商并发限制得到执行。
- [x] 单个任务失败有明确覆盖语义且不污染其他结果；现有 evaluator 没有该合同，任一 Send 任务异常会使整个子图失败，因此该硬门槛判定不通过并拒绝采用。
- [x] 配对实验验证与串行臂的候选资格、证据引用和报告一致。
- [x] 报告并发收益、延迟、调用数和复杂度；未通过门槛时删除实现。
- [x] 未采用，实验子图与开关已删除，因此条件性子图约束不适用。

## Answer

不采用。5 组 12 名候选完整图冻结数据配对中，最终报告与推荐顺序一致，但串行批量评估 p50/p95 为 31/82ms，`Send` 为 38/45ms，只有 1/5 组更快；每案来源读取从 4 次增至 24 次。实验将并发限制在 4，按 ID 去重。当前 evaluator 没有单候选错误覆盖合同，任一未处理 `Send` 失败会拒绝整个评估；提供部分结果需要改变领域合同。结果见 [`send-candidate-evaluation-paired.json`](../results/send-candidate-evaluation-paired.json)。

实验子图、开关和临时脚本已删除，正常路径继续使用单批次 evaluator。
