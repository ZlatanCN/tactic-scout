## 继承的设计约束

- 四类 active workflow snapshot 保留完整、已验证的结果，snapshot 与 TurnOutcome 在解释前一起提交。有效空结果也是完成结果，失败或中断不覆盖成功快照。[ADR-0010](../../docs/adr/0010-validated-workflow-snapshots-and-continuation.md)
- 已保存结果的解释使用其已验证快照，并区分本轮执行与 saved-result reuse。模型的事实主张仍需对应实际提供或合法复用的证据。[CONTEXT.md](../../CONTEXT.md)
- Checkpointer 负责线程状态和中断恢复；Store 负责明确确认的跨线程身份关系。后者记录身份指针与确认来源，不是全文或能力/表现数据仓库。[ADR-0011](../../docs/adr/0011-managed-persistence-and-confirmed-player-memory.md)

## 已核对的输入路径

- 请求理解：当前消息加结构化 conversationContext 投影，不是原始全文历史。目前所有线程本地别名均被放入该投影，因此结构化上下文本身仍可能随使用增长。[request-extraction.ts](../../src/request-extraction.ts)
- Lookup 工具循环：最近 HumanMessage 开始的本轮消息，包括本轮工具调用与结果。[assistant.ts](../../src/nodes/assistant.ts) · [player-mentions.ts](../../src/player-mentions.ts)
- 已保存查询结果追问、比较及推荐解释：当前用户消息加完整 resultJson。[assistant.ts](../../src/nodes/assistant.ts)

因此，历史消息长度、结构化别名/参与者数量与单次用户输入 / 工具结果大小是不同的预算来源。当前支持任意 OPENAI_MODEL 和自定义网关地址；模型窗口信息可能缺失，已安装模型的消息计数接口也不能单独证明包含工具/结构化输出 schema 的最终请求大小。Store 工作完成后，实施前需再次核对模型入口和 State schema。

额外的现有契约会约束缩减方式：比较必须覆盖全部确认参与者及范围覆盖说明；推荐解释必须保留返回的全部候选和排名顺序，不能静默只展示其中一部分。省略的投影字段也不能被解释成来源缺失。Lookup 的 assistant tool call 与 ToolMessage 必须保持对应 ID 和有效消息顺序。[assistant.ts](../../src/nodes/assistant.ts) · [execute-lookup-tools.ts](../../src/nodes/execute-lookup-tools.ts)

现有 eval 的 evidence collector 从实际模型输入中的 ToolMessage 和特定 JSON 提示标记提取证据。新增投影 / 分块 / 摘要输入格式时，需要相应记录实际交付的证据和覆盖范围，不能把完整持久化结果等同于模型已看到的结果。[observation.ts](../../evals/observation.ts)

## 设计树

已确定的根决策和仍待讨论的分支如下：

- Q1（已确认）：覆盖每次模型调用的完整输入预算，包括调用前检查、超长内容处理和 provider 超限后的恢复。
- Q2（已确认）：管理模型工作上下文；完整原始记录和已验证快照保持可追溯，checkpoint 回收 / TTL 另立议题。
- Q3（已确认）：允许有上限的额外调用处理大结果，以完整完成原任务为目标；仍无法完成时明确请求缩小范围。
- Q4（已确认）：预算配置优先；仅可信端点采用已知模型能力资料，未知窗口要求显式配置。
- Q5（已确认）：结构化证据通过精确字段 / 记录选择、分块或按需读取缩减；文字历史和过程说明适用摘要。
- Q6（已确认，按用户修正）：本轮用户输入导致超限时自动触发 compaction，不能默认立即要求用户缩短。原文保留。
- Q7（已确认）：优先压缩旧内容并保留本轮原文；单条消息自身超限时自动分块提取任务 / 条件并保留原文定位，每次辅助调用也受预算约束。
- Q8（已确认）：压缩结果、覆盖范围、原文引用和版本元数据随线程 checkpoint 保存，核对适用性后复用；不写入跨线程身份 Store。
- Q9（已确认）：保留现有 StateGraph，通过共享能力统一预算 / compaction / 恢复，各入口定义自己的业务证据选择规则。
- Q10（已确认）：按可用输入预算的 80% 软触发、60% 目标作为可配置初始值，每次发送前另做硬检查；可用预算考虑输出预留和误差余量。
- Q11（已确认）：摘要 / 分块提取默认沿用当前任务配置的模型和端点；允许显式配置独立压缩模型及其预算。
- Q12（已确认）：每请求最多 6 次额外模型调用 / 120 秒累计活动时间，任一先达到就停止，均可配置。失败 / 重试计数，恢复不重置已消费额度，现有重试和搜索上限继续生效。
- Q13（已确认）：完整已验证数据已有但解释未完成时，由程序展示完整数据 / 来源并说明解释未完成；数据或理解尚不完整时，不给出整体比较 / 排名结论。
- Q14（已确认）：仅因额度耗尽而停止时，用户明确要求继续可以追加一份新的有界额度，从保存的断点续接，历史消耗保留；普通恢复 / 重启不追加。
- 当前可决定的分支：
  - Q15：首版由程序按工作流选择 / 分块 / 回读证据，还是新增由模型自主调用的通用证据读取工具。
- 后续分支：
  - 完整证据与模型可见证据的关系。
  - 压缩元数据的生命周期、正常重启恢复和兼容性。
  - Token 计数、输出预留和安全余量。
  - 历史总结、确定性字段投影、旧工具内容清理、结果卸载 / 按需读取的适用场景。
  - 身份、来源、赛季、筛选条件、排名和数值在压缩后的完整性要求。
  - Saved-result reuse 与实际提供给模型的证据对应关系。

## 第二轮问题

### Q3：单份结果超出输入预算时是否自动处理

场景：一个新的比较请求返回许多球员的完整资料，即使没有历史消息，本次结果也无法一次放入模型。

建议：允许在明确的额外调用 / 成本上限内自动分批或按需处理，仍以用户要求的完整结果为目标；不能在限制内完成时，明确说明并请求缩小范围。具体处理策略和上限后续确定。

状态：已确认（用户：同意，2026-11-08）。

### Q4：未知模型窗口是否要求显式配置

建议：显式预算配置优先；可信标准端点可以使用已知模型的能力资料；模型窗口未知，或自定义网关无法确认实际限制时，要求配置输入窗口 / 预算，清楚提示缺失配置，不按模型名称猜测大窗口。具体配置和计数方法后续确定。

状态：已确认（用户：同意，2026-11-08）。

## 第三轮问题

### Q5：是否优先对结构化证据做精确选择，对文字历史做摘要

建议：球员身份、来源、赛季、指标、筛选条件和排名通过确定性字段 / 记录选择、分块或按需读取缩减输入；LLM 摘要用于文字过程说明和较旧对话。摘要可帮助定位证据，精确事实仍以对应的已验证记录为依据。

场景：只追问 xG 时，模型读取该球员对应来源 / 赛季 / xG 等必要字段；用户要求完整多人比较时，需要分批覆盖该请求所需的全部参与者和字段。完整原始结果仍按 Q2 保留。

状态：已确认（用户：其他的同意你，2026-11-08）。

### Q6：本轮用户指令本身超限时自动触发 compaction

## 第四轮问题

### Q7：是否先保留本轮原文，再处理单条消息自身超限

状态：已确认（用户：同意，2026-11-08）。

### Q8：是否随线程 checkpoint 保存并复用压缩结果

建议：已生成的压缩结果、覆盖范围、原文定位和版本等辅助元数据随线程 checkpoint 保存；仍与原始输入匹配时复用，正常重启后继续使用。原始消息和完整已验证结果依 Q2 保留。它属于线程工作上下文，不写入跨线程身份 Store。摘要更新 / 失效与兼容性细节后续确定。

## 第五轮问题

### Q9：是否在现有 StateGraph 中接入共享上下文管理能力

状态：已确认（用户：同意，2026-11-08）。

### Q10：是否采用提前触发线、压缩目标和发送前硬检查

建议：同时考虑模型实际总窗口、单独的输入上限、本次输出预留和计数误差余量，得到可用输入预算，避免对单独输入上限重复扣除输出。首版以该预算的 80% 作为 compaction 软触发线，60% 作为压缩目标；每次发送前仍检查完整请求是否满足硬上限。模型 / 入口均可配置。这两个比例只是待验收调优的初始值，不表示已有测量证明其最优，也不是保证所有输入一定能压到目标。

## 第六轮问题

### Q11：是否默认由当前任务模型完成摘要和分块提取

建议：默认沿用当前任务已经配置的模型和端点处理摘要 / 长输入分块，允许显式配置独立 compaction 模型及其窗口、输出预算和计数策略。不能通过切换到未配置的模型绕过 Q4；独立模型也遵守全部预算和证据规则。

状态：已确认（用户：同意，2026-11-08）。

### Q12：是否为新增上下文处理设置每轮统一的额外请求上限

建议：首版默认每个用户请求最多 6 次额外模型请求，并限制新增上下文处理的累计活动耗时为 120 秒，任一先达到就停止，可配置。活动耗时包括模型等待和自动恢复等待，不包括等待用户澄清或服务停机的时间。Compaction、分块提取和上下文超限恢复引入的额外请求共用该上限，失败和重试也计数；正常重启 / 原请求的中断恢复不重置已消费额度。每次调用仍有自己的输入 / 输出限额。现有每节点最多 3 次请求和每轮最多 3 次 lookup 搜索继续生效；新增处理不能利用新节点 / 再次进入节点绕开已消费预算。额度耗尽时的完整性与用户反馈在下一轮决定。

## 第七轮问题

### Q13：额度耗尽时是否区分完整数据与未完成解释

建议：如果完整、已验证的数据结果已经提交，但 compaction / 分批解释未完成，优先通过程序展示完整数据及来源（必要时分段），并明确说明文字解释未完成；不把局部模型解释冒充完整结论。如果数据或当前请求理解本身尚不完整，则说明已处理范围和限制，不输出全体比较 / 排名结论。完整结果和原文仍保留，后续可续接。

状态：已确认（用户：确定，2026-11-08）。

### Q14：用户明确要求继续时是否从断点追加有界处理额度

建议：仅因额度耗尽而停下时，应用中的用户明确请求继续，可以获得一份新的有上限处理额度，从已保存的断点和结果续接；历史消耗累计保留。普通恢复、正常重启和重复执行本身不自动增加额度。不重新查询已经完成的原始数据或重新排名，除非用户要求刷新或当前数据校验表明必须重做。遇到任务条件不明确 / 矛盾仍需澄清，不能用“继续”跳过。

状态：已确认（用户：确定，2026-11-08）。

## 第八轮问题

### Q15：首版是否由程序按工作流安排证据选择和分批

建议：首版由程序从已有完整输入 / 已验证结果中选字段和记录，安排分块、回读和覆盖校验，再把明确的一批证据交给模型。Lookup 保留当前受身份约束的搜索工具；本轮不新增由模型自主探索全部上下文的通用文件 / 证据检索工具。原文引用由共享能力和工作流用于定位、校验与后续回读。需要更开放的证据探索时，再基于明确场景扩展模型可调用工具。

理由：当前工作流和结果 schema 明确，程序驱动的方式更容易保持全部参与者 / 候选覆盖、原排名、来源边界和调用上限；原始输入与结果已经在 checkpoint / snapshot 中，无需仅为这一能力另建通用文件系统。

状态：已确认（用户：是，2026-11-08）。

## 实施方案中需要明确的工程契约

以下是已接受方向下必须补齐的工程细节，不等同于另行接受的用户体验选择：

- 完整请求计数包含系统指令、工具 / 结构化输出 schema、消息、协议开销和输出预留；计数结果注明其估算性质，provider 实际返回 overflow 时仍需有界恢复。
- 单条长输入的分块提取需要校验全部参与者、否定 / 排除条件、日期 / 赛季、数值及跨块指代；后文修改前文条件与真正矛盾分别处理。不能把各块独立摘要直接拼接后就执行。
- 输入 overflow、结构化输出解析失败和输出被截断是不同结果。预留输出并不能保证回答完整；必须检查终止原因和覆盖范围，有限续写 / 分批仍纳入额外预算。
- 保留精确任务锚点和原文引用，重复 compaction 时可以从原文重建；不能仅依赖不断概括的上一版摘要。
- 压缩缓存以来源消息 / 范围 / hash、依赖快照和格式版本校验。辅助缓存失效时丢弃重建，与整个线程 State schema 不兼容分开处理。
- 追踪交付给模型的实际字段 / 记录，与确定性回答渲染器直接读取完整 resultJson 的证据分开记账；不得把未传入模型的记录冒称为模型已看到。
- 达不到 60% 压缩目标时，若输入仍满足硬上限且没有缺失必要信息，可继续执行；同一内容没有缩减进展时不能反复压缩。
- 正常重启、native interrupt 恢复和用户发起新的任务需要区分预算生命周期；已消费请求额度不能因恢复而清零。
