# LangChain and LangGraph context management

**Checked:** 2026-11-08
**Question:** Which official JS/TS runtime mechanisms can control token and message growth, where do they run, and what remains application-owned?

本调研先于本功能的设计决定；“当前项目”描述是讨论开始时的实现基线。后续确认的计划和技术规则见 [plan.md](plan.md)、[spec.md](spec.md) 和 ADR-0012。

## Summary

LangGraph’s low-level `StateGraph` persists and updates state; it does not automatically compact the messages a node sends to a model. The model node chooses its prompt from state, so trimming, summarization, and tool-output limits must be implemented at that boundary or provided by an agent harness. Checkpointing keeps thread state and recovery history; it is not context-window management. [LangGraph JS memory guide](https://github.com/langchain-ai/langgraphjs/blob/main/docs/docs/concepts/memory.md) · [LangGraph JS checkpointer reference](https://langchain-ai.github.io/langgraphjs/reference/modules/langgraph-checkpoint.html)

LangChain JS provides opt-in `createAgent` middleware for summarizing history and clearing old tool results. Low-level message utilities provide trimming and deletion primitives. Deep Agents (`createDeepAgent`) is a separate, more opinionated harness with automatic offloading and summarization. These layers are related but not interchangeable: installing or using LangGraph alone does not enable LangChain middleware or Deep Agents compression. [Middleware overview](https://docs.langchain.com/oss/javascript/langchain/middleware/overview) · [Deep Agents context engineering](https://docs.langchain.com/oss/javascript/deepagents/context-engineering)

## Supported mechanisms

| Mechanism | Where it operates | Supported behavior | Limits and configuration |
| --- | --- | --- | --- |
| `trimMessages` from `@langchain/core/messages` | A model-call prompt, when the application invokes it | Keeps a bounded slice by token count, with boundary controls such as `startOn`, `endOn`, and `includeSystem`. A model can provide the token counter, or the caller can provide one. | A utility, not an automatic graph policy. It only changes the prompt unless the caller also writes a deletion/update to graph state. Choose the budget for the target model and preserve valid provider message/tool-call ordering. [LangGraph JS memory guide](https://github.com/langchain-ai/langgraphjs/blob/main/docs/docs/concepts/memory.md) |
| `RemoveMessage` / `REMOVE_ALL_MESSAGES` | A graph state update using the LangGraph messages reducer (`MessagesValue`, `MessagesAnnotation`, or equivalent) | Deletes identified messages or clears the message list. LangGraph discards the removal marker after applying it. Can be used in a node or `createAgent` `beforeModel` hook. | The resulting message sequence must remain valid for the model provider; tool-call assistant messages normally need their matching tool result. Deleting from current state does not imply older checkpoint snapshots are erased. [LangGraph JS memory guide](https://github.com/langchain-ai/langgraphjs/blob/main/docs/docs/concepts/memory.md) · [LangChain short-term memory guide](https://docs.langchain.com/oss/javascript/langchain/short-term-memory) |
| `summarizationMiddleware` | Opt-in LangChain `createAgent` lifecycle, before a model call | Summarizes older conversation messages when configured thresholds are met, then retains recent context. JS options include `trigger` and `keep` thresholds by tokens, messages, or model-context fraction; a custom token counter and summary model/prompt can be supplied. | Not automatically applied to a standalone `StateGraph` model node. Default counting is character-based approximation; fractional limits depend on model profile data (the docs call this out for `langchain@1.1.0`). Summarization is text-oriented; it does not shrink multimodal payloads and can lose detail. It also makes a separate model call. [Built-in middleware docs](https://docs.langchain.com/oss/javascript/langchain/middleware/built-in) |
| `contextEditingMiddleware` + `ClearToolUsesEdit` | Opt-in LangChain `createAgent` lifecycle | On a token threshold, clears older tool outputs, preserves the most recent `keep` tool results, and can retain or clear call arguments. JS options include `triggerTokens`, `keep`, `clearToolInputs`, `excludeTools`, and `placeholder`. | Clears old tool output; it is not a summarizer and cannot make a single oversized newest result small. Application tools should still cap or externalize large responses. Not automatically active on a custom low-level graph. [Built-in middleware docs](https://docs.langchain.com/oss/javascript/langchain/middleware/built-in) |
| Deep Agents automatic compression | `createDeepAgent` harness | Large tool results above the documented default of 20,000 tokens are offloaded to its configured backend and replaced by a file reference plus a preview. Redundant large file-write/edit call inputs are replaced with filesystem pointers as the session approaches 85% of the model window. Its summarization keeps 10% recent context and writes the original conversation to filesystem. | This is Deep Agents behavior, not a LangGraph default. Accurate counting, in-model summarization via `wrapModelCall`, and automatic `ContextOverflowError` fallback/retry require `deepagents >= 1.6.0`. It does not resize image payloads. [Deep Agents context engineering](https://docs.langchain.com/oss/javascript/deepagents/context-engineering) |

LangChain’s middleware is composed into `createAgent`’s loop. The official JS docs also show a `createAgent` instance placed inside a larger `StateGraph`, where its hooks continue to run. A hand-written model node remains outside that middleware unless the graph explicitly uses such an agent node or implements equivalent prompt/state updates. [Middleware overview](https://docs.langchain.com/oss/javascript/langchain/middleware/overview)

LangGraph `runtime.context` is per-run application configuration, not prompt text by default. Tools, middleware, or nodes must read it and explicitly add any desired values to model messages. This distinction avoids treating runtime metadata as if it consumed context-window tokens automatically. [Deep Agents context engineering](https://docs.langchain.com/oss/javascript/deepagents/context-engineering)

## Checkpoint semantics and prompt budgeting

A checkpointer stores graph-state snapshots per thread (typically at graph supersteps) to support continuation, interrupts, recovery, and history inspection. Persisting a long `messages` state does not automatically pass all of it to the model; a node controls the model input. The official memory guidance explicitly warns that long message histories can exceed model windows and recommends trimming, deleting, summarizing, or custom filtering. Checkpoint history can also grow independently; the JS persistence guide recommends retention/pruning for long-running threads. [LangGraph JS persistence guide](https://langchain-ai.github.io/langgraphjs/how-tos/persistence-postgres/) · [LangGraph JS memory guide](https://github.com/langchain-ai/langgraphjs/blob/main/docs/docs/concepts/memory.md)

For a reliable budget, the application must set a safety margin below the selected model’s input limit and account for the complete request: system/developer prompt, tool schemas, current user content, retained history, tool results, and reserved output. Middleware thresholds are triggers based on the configured counter/profile; they are not a guarantee that every provider’s final serialized request fits. Bound large tool outputs before they enter state, decide which information may be summarized or removed, and retain task-critical structured state outside conversational messages when it must survive trimming. These are application-design consequences of the documented primitives, not automatic LangGraph policies.

## Version status and fit for this repository

As checked on 2026-11-08, the official LangChain JS docs include both middleware APIs. The lockfile resolves `@langchain/core@1.3.0`, `@langchain/langgraph@1.5.2`, and `@langchain/langgraph-checkpoint@1.2.1`; the project has no direct `langchain` or `deepagents` dependency. `trimMessages` and `RemoveMessage` are exported by the installed `@langchain/core` runtime. [LangChain JS releases](https://github.com/langchain-ai/langchainjs/releases) · [repository package manifest](../../package.json) · [repository lockfile](../../pnpm-lock.yaml)

The current graph extends `MessagesZodState` in [`src/state.ts`](../../src/state.ts). Its lookup assistant constructs its model request from the current turn plus the lookup system prompt in [`src/nodes/assistant.ts`](../../src/nodes/assistant.ts), avoiding prior conversation turns on that call. Comparison and recommendation answer calls separately inject the full structured `outcome.resultJson` into a new user message ([`assistant.ts`](../../src/nodes/assistant.ts)). **Inference for this project:** overflow risk therefore centers on a very long current-turn input, prompt/tool-schema size, or a large lookup/tool/workflow result; persistent checkpoint growth is a separate storage concern. There is no compaction policy recorded in the reviewed ADRs and no ADR explaining the omission. The existing setup can use core message utilities directly; using the prebuilt middleware requires adopting `langchain`’s `createAgent` loop (possibly as a graph node) or writing equivalent logic in the current graph. The Deep Agents automatic policy requires a separate harness/package and its filesystem backend behavior.

## Patterns in open-source projects

### LangAlpha: multiple budgets and externalized data

LangAlpha documents its core agent as a LangGraph application assembled with `langchain.agents.create_agent()` and a middleware stack. Its [`agent_config.yaml`](https://github.com/ginlix-ai/LangAlpha/blob/main/agent_config.yaml) enables compaction at 120,000 tokens, keeps the latest 10 messages, starts truncating old tool-call arguments at 40 messages, protects the last 10, and caps each argument value at 2,000 characters. Its README also describes large tool results being offloaded to the workspace with a short preview, subagents returning synthesized results into isolated parent contexts, and Python sandbox execution for processing large financial tables before returning only computed outputs to the model. This combines history summarization, argument pruning, data offload, programmatic data processing, and subagent isolation. [Architecture](https://github.com/ginlix-ai/LangAlpha/blob/main/AGENTS.md) · [README](https://github.com/ginlix-ai/LangAlpha)

### Open Deep Research: task-specific compression nodes

Open Deep Research uses a hand-built LangGraph `StateGraph` with LangChain models. Its researcher subgraph ends at a `compress_research` node, which calls a configurable compression model and returns both a concise `compressed_research` result and separate `raw_notes`; the supervisor sends the summary onward and retains raw notes in its own state. Final report generation detects token-limit errors, starts with a character budget estimated as four times the configured model token limit, and reduces that budget by 10% on later retries. Its research-compression fallback calls `remove_up_to_last_ai_message` and retries up to three times. [Research graph source](https://github.com/langchain-ai/open_deep_research/blob/main/src/open_deep_research/deep_researcher.py) · [token-limit helpers](https://github.com/langchain-ai/open_deep_research/blob/main/src/open_deep_research/utils.py)

There is an open project issue pointing out that the helper name/comment and implementation disagree: it returns the message prefix before the last AI message, which removes the most recent suffix. This is a useful reminder that custom overflow fallbacks need tests for which evidence they retain. [Issue #252](https://github.com/langchain-ai/open_deep_research/issues/252)

### Deep Agents: automatic summary plus archive

Deep Agents includes a summarization middleware in its default stack. It presents a summary and recent tail to the model and offloads evicted history to its configured backend so the original conversation remains retrievable. It also has an explicit tool-result offload path for oversized outputs. [Middleware implementation](https://github.com/langchain-ai/deepagents/blob/main/libs/deepagents/deepagents/middleware/summarization.py) · [architecture](https://github.com/langchain-ai/deepagents/blob/main/libs/ARCHITECTURE.md) · [context engineering docs](https://docs.langchain.com/oss/javascript/deepagents/context-engineering)

Across these projects, the common pattern is to use multiple controls at the point where the model prompt is assembled: reduce repeated tool argument payloads, move bulky data to files or a sandbox, isolate long subtasks, and summarize only the conversation portions that need to carry forward. Applications retain source data or raw notes outside the compact model-facing context when later retrieval or verification matters.

## Existing evaluation usage and its limits

Read-only inspection of archived V43 held-out and development reports found provider-reported token usage for ordinary requests. Across the two inspected reports the largest reported Agent input was 6,236 tokens and output 712 tokens. These cases cover only two or three comparison participants, up to four player-recommendation candidates, and up to two team-recommendation candidates. They do not establish safe output reservations for the runtime's allowed 20 candidates per separate list, unbounded comparison participants, long user inputs, or overflow recovery. The proposed 80% / 60% thresholds are explicitly configurable design defaults, not conclusions from these reports. [V43 report](../../.data/evals/v43-heldout-runs/81a665f6-61e2-44b0-9ab1-1b46a84a781d/report.md) · [development report](../../.data/evals/final-dev-runs13/615ed820-7097-465a-b35d-6ef74c71d5f5/report.md)

The current configured model sets no output-token cap. Existing per-node request budgets count retries / structured-output repair, and lookup has a separate three-search limit; neither creates a global bound for newly added multi-node compaction / chunk-processing calls. A separate shared allowance is therefore a design requirement to be decided alongside the new behavior.
