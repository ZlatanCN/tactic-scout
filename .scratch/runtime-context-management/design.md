# 运行时上下文管理技术细则

Status: resolved

完整设计已于 2026-11-08 在 Q16 获得用户确认。本文保留技术细则，正式功能规格见 [spec.md](spec.md)。Store 实现已完成；开始本功能实现前核对其最终基线。

设计与实施顺序：[plan.md](plan.md)。讨论记录：[discussion.md](discussion.md)。依据：[research.md](research.md)、[ADR-0012](../../docs/adr/0012-model-input-budget-and-persisted-evidence.md)。

## 1. 目标与边界

对每次实际模型调用准备有界输入，包括请求理解、lookup 模型 / 工具循环、执行结果解释、已保存结果追问，以及本功能新增的摘要 / 分块提取 / 恢复调用。

- 保留当前 StateGraph、身份解析 / 澄清入口、确定性比较 / 推荐和四类完整已验证快照。
- 只缩减模型工作上下文。完整消息、工具原始结果和权威 workflow result 保持可追溯；checkpoint 存储回收 / TTL 属于另一项工作。
- 首版由程序按工作流选择字段、安排分块和原文回读。Lookup 沿用原有受身份约束的搜索工具；不新增模型可自由探索全部上下文的通用文件 / 证据检索工具。
- 不因持久化消息列表很长，就把本来不进入模型的所有旧消息重新送入摘要。触发依据是本次实际组装的请求。

## 2. 共享能力与模块边界

保留 `src/agent.ts` 为图组装入口。用目的明确的共享模块封装配置解析、输入估算、内容选择调度、compaction、预算记账和准备结果；各入口提供其业务证据选择规则。只有真实 graph node 放入 `src/nodes/`，不建立通用 `utils/` 层，不让 `player-data` 依赖图 State。[ADR-0003](../../docs/adr/0003-codebase-module-boundaries.md)

对调用方暴露三类准备结果：

1. **可调用**：准备好的 messages、工具 / 结构化输出 schema、模型输出限额、预算说明和证据覆盖信息。
2. **需自动处理**：待处理内容范围、处理阶段 / 进度、原文引用和剩余额度。程序推进处理后重新检查。
3. **不能继续**：明确区分配置缺失、额度耗尽、指令歧义、证据未完成、外部处理失败、无法恢复的溢出。不得用空摘要伪装成功。

不可在一个模型节点内部进行不可见的无界摘要循环。需要跨调用恢复的处理进度与额度，在有 checkpoint 的图步骤边界提交；组合方式应符合现有业务节点和 native interrupt 的生命周期。

## 3. 模型能力与完整请求预算

### 能力来源

- 显式配置优先，其匹配范围包括端点、模型和调用用途。
- 可信标准端点可采用已知模型资料。自定义网关或模型实际窗口无法确认时，需要显式配置；不能仅按同名模型推断窗口。
- 主任务模型与单独配置的压缩模型各自解析能力。压缩默认沿用当前任务的模型和端点。
- 每种调用用途必须解析出有限的输出 token 上限，并实际用于 API 请求。可继承已有明确上限或显式配置；不能把未知的 provider 默认输出额度当作零。实现时需交付可用的预算配置示例。
- 区分共享的上下文总窗口、独立输入上限和独立输出上限。源资料不能说明其语义时，按未知配置处理。

### 预算计算

在对应限制存在时取交集：

```text
原始输入上限 = min(独立输入上限, 共享总窗口 - 本次输出上限)
可用输入预算 = 原始输入上限 - 计数误差余量
软触发线     = 可用输入预算 × 80%
压缩目标     = 可用输入预算 × 60%
```

只有独立输入限制时，不重复扣除已分离的输出额度。输出上限还需满足模型独立输出限制。预算必须为正，且基础系统指令和必要 schema 能装下；否则是配置 / 请求构造失败，不能要求用户靠缩短业务请求修复。

计数包括实际发送的全部系统指令、消息、现代 tool calls / results、工具 schema、结构化输出 schema 和协议开销。优先使用适配当前模型 / 协议的本地计数；现有 SDK 的消息计数不足以单独证明包含全部 schema 的最终请求大小。只能估算时，必须注明计数方法并配置正的误差余量。余量和各用途输出额度由实现阶段的边界用例确定并可配置，不从已有普通评测样本推导通用保证。

每次发送前执行硬检查，包括辅助压缩调用。80% / 60% 是可调初始值；无法压到 60% 但必要信息完整、请求仍符合硬上限时允许继续。无可压内容或同一输入无缩减进展时，不反复触发相同处理。

## 4. 内容选择与自动 compaction

### 请求理解

- 保留本轮用户指令、必要 focus、上一轮任务摘要、相关 active workflow 的参与者 / 条件，以及与本轮提及或焦点相关的线程别名。
- 本地别名选择沿用已有名称规范化和已解析引用；不能靠近似姓名、最近记录或摘要新建身份关系。
- 仍有多个可续接工作流时，按已有规则澄清，不能为减少输入自行丢掉另一种可能。
- 结构化上下文本身也计入预算；不得继续全量注入无限增长的别名列表。

### 文字历史

优先移除选中输入内的重复过程信息，对较旧文字过程生成带来源引用的任务摘要，保留精确的目标、排除 / 否定条件、日期 / 赛季、关键 ID、已确认决定和进行中步骤。本轮原文能在压缩旧内容后装下时保持原样。

摘要是辅助表示，不是新的球员身份、用户确认或来源事实。重复压缩时保留精确锚点和原文访问路径，必要时从原文重建，不只反复概括上一版摘要。原文的指令 / 引用材料角色边界在压缩后保持，不能把引用内容升级为系统指令。

### 单条用户输入自身超限

自动按文本 / 结构边界分块，每一块的提取请求都经过预算检查。产出可合并的任务 / 条件清单及原文定位，并核对：

- 所有参与者、参考对象、排除对象和团队提及；
- 数值、单位、赛季、赛事、位置及其他明确限制；
- 跨块指代、后文明确修正前文条件，以及真正的矛盾；
- 每一项原文引用是否仍匹配对应消息和内容版本。

不能把独立块的摘要简单拼接后直接执行。确定性校验可验证引用、ID、数量和支持的条件形状；任意自然语言意图的语义保真还需要后述续接评测，不能因 JSON 合法就宣称完全保真。校验失败时有限回读 / 修复；仍有歧义则用已有 pending clarification 澄清并保留处理进度。

Compaction 调用自身过大时由程序减小源内容批次，不能递归启动无限的“压缩压缩器”流程。

## 5. 结构化证据投影和分批解释

所有投影从 owning schema 校验后的完整 result 产生，原始 resultJson 和 active snapshot 不被部分视图替换。每批带有来源结果引用 / digest、记录引用、已选择字段和覆盖范围。程序据此决定剩余批次及回读；模型不自行更换来源 ID。

必须区分：来源有数值、来源明确 null、字段未选择、来源不可用、该来源未查询。字段没进入投影不能被说成源数据缺失。

各工作流的必要语义：

| 工作流 | 投影与最终交付必须保留的内容 |
| --- | --- |
| Lookup | 精确 provider/source ID、canonical 与未链接身份关系、查询来源及其状态、显式请求赛季与默认赛季的区别、实际赛事 / 赛季、所问字段及解释缺失值所需上下文。 |
| Comparison | 全部确认参与者、各来源记录、scope 的赛事 / 赛季、覆盖人数和 `coversAllParticipants`、全体共同范围数量；局部范围不能被说成覆盖所有参与者。 |
| Player recommendation | 两份候选列表分别完整保留和维持原排名；每行姓名、FM ID、年龄、位置评分、CA、PA、currentDistance；参考画像、目标位置、年龄计算日期、FM 日期、筛选条件和阶段计数。 |
| Team recommendation | 上述候选与筛选语义，加团队身份、阵容来源 / 获取日期、FM 日期、mapping coverage / 方法、实际参考对象、rankingBasis 和当前阵容身份排除范围。 |

分批解释不得重新排名、补算不存在的字段或对未覆盖的全体作比较结论。批次结果明确覆盖哪些记录和哪些问题；合并前核验必要参与者 / 候选和字段的覆盖。需要程序合并或完整数据渲染时保留原始值和顺序。

Lookup 输入投影仍保持 AI tool calls 与 ToolMessage 的配对、原 tool_call_id 和有效协议顺序；减少内容不等于删掉配对的工具响应。原始工具内容继续保存。

Saved-result reuse 使用原完整快照及原日期，证据读取不触发新的 provider 查询或排名。外部数据集更新本身不会改写已有历史结果，也不会使其解释自动转为刷新查询。只有新数据计算才按已有身份再校验和 provider/cache 规则执行；历史结果的投影以该结果的内容和来源版本为准。

## 6. 线程内元数据与兼容性

以线程内可校验的辅助元数据记录：源消息 ID / 范围 / 内容 hash、结果引用与 digest、精确任务锚点、摘要 / 投影格式版本、已处理与剩余批次、来源字段覆盖，以及预算 grant / reservation / consumption。

- 只有来源、相关快照和格式版本仍匹配时复用压缩结果。
- 新内容在已有范围之外可继续处理；已覆盖内容被修改、分支改变、依赖结果改变或辅助格式不兼容时，丢弃相应缓存并从原文重建。
- 辅助缓存失效不自动让整个线程不可用；主 State 本身不兼容时仍遵守 Store 工作确定的 schema 兼容性边界。
- 这些信息随 native checkpointer 保存，正常停机 / 重启后经用户触发续接。不复制到跨线程身份 Store，不修改已确认身份关系。
- 不增加独立的持久化 `activeTask` 指针来替代已有 request/outcome/四类快照的续接规则。

## 7. 额外调用、活动时间和恢复

每个用户请求有一份上下文处理 grant，默认允许 6 次额外模型请求和 120 秒累计活动处理时间，任一先到即停止；均可配置。辅助摘要、分块提取、分批解释 / 中间聚合和 context-overflow 恢复所新增的请求共用额度，失败与重试也计数。每个请求仍受独立输入 / 输出限制；模型价格未知时报告调用和 token 用量，不声称精确金额保证。

固定计数口径：所有新增摘要、分块提取、证据批次解释和辅助中间合并调用都是额外调用，包含其失败 / 重试。原业务入口最终生成一次业务回答或结构化请求的调用，仍使用原业务调用预算；它经过 context-overflow 缩减后再发送的恢复请求同时计入额外额度和原调用的尝试上限。例如一次解释变成 N 次批次解释加一次最终回答，则 N 次批次解释均计额外，最终回答占原有调用；如果直接程序合成、不再调用最终模型，不能把其中一批改名为“原调用”免计额度。原 lookup 工具循环按既有预算运行，压缩流程不得增设无额度约束的业务调用。操作分类和稳定 ID 随进度保存，恢复后不重新选择免费调用。

现有每节点三次请求、结构化提取至多一次修复、每轮三次 lookup 搜索及外部边界的超时 / 重试分类继续有效。新增节点 / 再次进入节点不会刷新总 grant。首版按程序安排有界批次，避免内部并发放大额度。必要时将准备 / 预留和外部调用拆到可提交 checkpoint 的步骤；不能只在节点结束后才记录全部消耗。

调用前预留额度，完成后按已知结果结算；中断后无法确认是否完成的已开始调用保守视为已消耗，继续执行前重新检查剩余额度。可以重复只读外部调用，但不承诺 exactly-once。正常恢复不能反复使用同一份不确定额度。

活动时间包含模型等待和自动恢复 / backoff，排除用户等待和服务停机。为调用附上现有单次超时与剩余活动时间中更短的截止时间，取消 / 耗尽后及时退出。正常重启 / 原请求的 native interrupt 恢复不重置 grant。

额外活动时间覆盖新增上下文选择 / 压缩 / 分块 / 恢复阶段，原业务调用沿用原超时。对中断后无法确定完成情况的操作，使用已持久化的调用 / 时间预留上界保守结算，可能比可观测的实际耗时更早耗尽额度；停机期间不按墙钟累加。额度耗尽后只做必要的有界提交、取消和确定性交付，不再发出模型调用。

### Provider 报输入溢出

将可识别的 context-overflow 与鉴权、配额、配置错误、普通暂时故障分开。计数估算通过后仍可能溢出：保存执行事实，缩减有效源批次后有限重发。新请求必须有缩减进展，且仍受节点和共享总预算约束。不能把相同超限 payload 当暂时故障重复发送。

### 输出截断

检查 provider 的终止原因、结构化结果是否完整以及候选 / 参与者覆盖。预留输出并不保证生成完成。可在剩余预算内有限续写或按批重新解释；不能把截断响应标为完整 answer，也不能把中间摘要追加成最终聊天回答。输出 / 流式消费路径需明确内部处理与最终交付的区别。

### 失败与额度耗尽

- 数据完整且已验证：程序展示完整数据和来源，必要时分段，明确说明解释未完成。有效空结果按完整空结果处理。
- 数据或任务理解不完整：说明已处理范围和限制，不给出全体比较 / 排名结论，不把不完整草稿覆盖成功快照。
- 保留已提交结果、原文、批次进度和消耗；不得因解释失败删除已经完成的数据。
- 仅因上下文调用 / 活动时间额度耗尽而停止、且原请求及进度仍有效时，用户明确要求继续才创建新 grant（默认同样上限），保留历史消耗并从断点续接；用来源用户消息 / 确认 ID 使重复提交幂等。配置、鉴权、未修复的契约错误或条件歧义不能靠“继续”自动拨款并重试。普通恢复和重启不自动拨款。
- Grant 和处理进度绑定明确的线程 / 原请求及其源内容；不把另一项新任务的额度、摘要或进度自动带入当前任务。续接目标不明确时沿用澄清规则。
- 多个可能的续接目标、矛盾条件或无法确认的约束需要澄清；“继续”不等于绕过这些检查。用户要求刷新时才按正常路径重查 / 重新排名。

## 8. 可观察性与证据评估

每次调用记录用途、模型预算来源、计数方法、估算输入 / 输出上限、可用预算、压缩前后规模、覆盖 / 引用、stop reason、额外调用及活动时间消耗、provider 实际 token usage（若有）。日志不写原始提示或阵容数据，沿用 ADR-0008 的日志边界。

评估和 trace 区分三类材料：完整保存的原始结果、实际交付给模型的投影 / 批次、确定性渲染直接读取的记录。只有后两者按各自用途成为生成 / 渲染事实的依据，不能把未交付模型的字段冒称为模型已见证据。更新现有仅依赖 ToolMessage / 特定 JSON 文案标记的 collector，兼容未压缩路径。摘要本身不能成为新造数字或身份的权威来源。

## 9. 验收要求

以隔离 checkpointer / Store、可控 fake model/provider 和小预算强制触发边界；复用已完成 Store 工作的真实 Dev Server 临时存储 harness 验证正常重启。测试不读取或清理用户真实 `.langgraph_api`。

| 场景 | 必须验证的行为 |
| --- | --- |
| 正常小请求 | 所有模型入口有预算；无需压缩时无额外摘要调用，原路由、身份和正常结果语义保持。 |
| 窗口与计数 | 未知网关窗口缺配置时调用前明确失败；工具 / 结构化输出 schema 计入预算；输出额度确实传入请求；基础指令本身过大与用户长消息分别处理。 |
| 长别名 / 旧历史 | 实际输入有界，焦点、四类快照、同名歧义和已确认引用保持；不重新加载无关原始历史。 |
| 超长本轮用户输入 | 自动处理；跨块名字、排除 / 否定、数值、后文修正和指代能保留，引用对应原文；摘要请求自身不超限。 |
| 大型结果 | 覆盖两个各 20 人的推荐列表和多人比较，排名、必需字段、scope coverage、缺失值与省略字段含义保持。 |
| 已保存结果追问 | 准确读取原快照，原日期保持，不再次查询 provider 或重新排名。 |
| Provider 实际 overflow | 有界缩减后重试，payload 有进展；调用 / 时间额度继续累计；鉴权等错误不误触发 compaction。 |
| 输出被截断 | 不当作完成，有限恢复；耗尽后按数据完整性正确交付。 |
| 预算及用户续接 | 6 次 / 120 秒边界、失败重试计数、恢复不清零；显式继续只新增一份 grant，重复提交不重复拨款。 |
| 正常重启 | 已生成摘要 / 覆盖 / 进度和消耗可恢复；对中途未知完成的调用保守记账，不承诺 exactly-once。 |
| 重复压缩 / 缓存失效 | 多轮后仍能遵守早期精确约束；源内容 / 快照 / 版本改变时失效重建，辅助缓存错误不误判整个线程不兼容。 |
| 数据与解释完整性 | 完整数据可确定性展示全部记录；不完整数据不产生整体结论，既有成功快照保留。 |
| Evidence trace / eval | 实际模型证据、渲染证据及原始存储能区分，覆盖信息准确，摘要不升级为身份确认。 |
| 用户可见响应 | 内部摘要 / 草稿不作为最终回答；进度、限制和继续方式清楚。 |

固定边界用例与相关现有回归通过后，再以续接型评测观察压缩前后事实依据、任务完成和多次压缩漂移。历史 V43 只作普通案例基线，不据此声称压力场景已通过；本设计阶段不启动 live 模型评测。
