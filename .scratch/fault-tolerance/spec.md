# Project-wide LangGraph fault tolerance v1

Status: resolved
Labels: ready-for-human

## Problem Statement

A scout can complete player lookup, player comparison, player recommendation, and team-directed recommendation, but the reliability of the conversation still depends on every model and provider call completing correctly. A temporary network interruption or stalled call can abort a run; a malformed structured request can fail before a new request is recorded; repeated lookup tool calls can consume unnecessary work. Provider errors are currently too coarse to distinguish a temporary service failure from exhausted quota or invalid data, and broad catches can conceal programming errors.

The scout needs predictable failure behavior across the entire project: bounded waiting and requests, safe retries, a clear explanation when recovery is exhausted, and preservation of successful conversation context. The maintainer needs to diagnose these events without collecting prompts, credentials, or raw roster data in application logs or State.

## Solution

Apply one project-wide fault policy through the appropriate LangGraph node boundaries, provider adapters, model calls, and lookup Agent loop. Retry only recognized transient provider failures; bound physical provider requests, external-attempt time, structured-output repair, and lookup tool execution. Use native LangGraph retries, timeouts, and error handlers where they enforce the agreed behavior, while keeping expected domain outcomes and human clarification as ordinary graph control flow.

After a known external failure is exhausted, return a deterministic, task-appropriate failure response and retain completed business results. Unexpected programming errors remain visible to the caller. Continue using an isolated MemorySaver per graph instance and thread-scoped checkpoints; this version provides recovery within the running process, without promising recovery after a process restart.

## User Stories

1. As a scout, I want a temporary provider connection failure to recover automatically, so that a brief network interruption does not force me to repeat my request.
2. As a scout, I want temporary server failures to receive a bounded number of retries, so that the agent can recover without waiting indefinitely.
3. As a scout, I want each external API attempt to stop after 15 seconds, so that a stalled football-data service cannot leave the conversation hanging.
4. As a scout, I want each model request to stop after 60 seconds, so that a stalled model gateway cannot leave the conversation hanging.
5. As a project owner, I want no more than three physical provider requests for one logical node activation, so that retry behavior has a predictable cost.
6. As a project owner, I want SDK retries to be disabled or included in that same budget, so that a graph attempt cannot silently multiply requests.
7. As a scout, I want short rate limits and exhausted daily quota treated differently, so that the agent waits only when recovery is supported by provider evidence.
8. As a project owner, I want a short 429 rate limit retried at most once within the three-request budget, so that rate-limit handling cannot expand the total request count.
9. As a scout, I want exhausted daily quota reported immediately, so that repeated requests do not waste time or remaining service capacity.
10. As a scout, I want a missing or invalid credential reported without retries, so that the agent identifies a configuration problem clearly.
11. As a scout, I want malformed football-provider responses treated as invalid data, so that the agent does not repeatedly request or fabricate a roster.
12. As a scout, I want unresolved player identity to remain a clarification, so that identity uncertainty is not mistaken for a network fault.
13. As a scout, I want unsupported positions and filters to remain explicit domain outcomes, so that the agent does not weaken my request during recovery.
14. As a scout, I want a completed empty candidate list treated as a successful result, so that an empty list does not trigger needless retries.
15. As a scout, I want malformed structured request output to receive one validation-guided repair, so that a recoverable formatting error does not end the turn immediately.
16. As a project owner, I want the repair request included in the same maximum of three model requests, so that formatting recovery cannot create a second retry budget.
17. As a scout, I want a repair to preserve my original message and confirmed conversation context, so that recovery does not change which players or team I meant.
18. As a scout, I want a clear response when structured request repair also fails, so that I know the new request was not executed.
19. As a scout, I want request-understanding failure to skip identity resolution and data tools, so that the agent cannot accidentally execute the previous turn's request.
20. As a scout, I want a model outage during player lookup handled without changing the confirmed source IDs, so that recovery cannot query a different person or source record.
21. As a scout, I want a model outage during final explanation to leave the completed lookup, comparison, or recommendation available, so that successful data work is not lost.
22. As a scout, I want an exhausted explanation request to produce a deterministic failure response, so that error handling does not depend on calling the same unavailable model again.
23. As a scout, I want each lookup turn limited to three search tool executions, so that a model repeatedly asking for the same data cannot loop indefinitely.
24. As a project owner, I want tool calls batched into one model response to count individually toward that limit, so that parallel-looking calls cannot bypass the cap.
25. As a scout, I want a clear limit response when another search would exceed the cap, so that the agent does not silently drop a tool call or pretend the task finished normally.
26. As a scout, I want a new user turn to receive a fresh lookup allowance, so that a prior turn's work does not consume the next turn's budget.
27. As a scout, I want failed lookup, comparison, and recommendation attempts to preserve the last successful Active lookup, Active comparison, Active recommendation, and Active team recommendation, so that I can continue a useful conversation after an outage.
28. As a scout, I want a failed team request to stop before ranking from an incomplete roster, so that recovery cannot recommend a possible current squad member.
29. As a scout, I want a human identity or position clarification to pause normally, so that waiting for my answer is not retried or treated as an external failure.
30. As a scout, I want Command resume to continue the same clarified request, so that confirmed player identities and roster mappings are retained.
31. As a project owner, I want each thread and node activation to own its budgets independently, so that simultaneous conversations cannot consume or reset one another's allowances.
32. As a scout, I want cancellation to stop current work and further retries, so that an abandoned request cannot keep making provider calls.
33. As a project owner, I want HTTP and model clients to observe attempt cancellation, so that a graph timeout does not leave an avoidable request running in the background.
34. As a scout, I want responses arriving after timeout or cancellation ignored, so that stale results cannot overwrite the current turn's State.
35. As a project owner, I want failed or late provider responses excluded from the successful roster cache, so that later requests cannot receive invalid or canceled work as a cache hit.
36. As a scout, I want the existing successful seven-day roster cache to remain usable during recovery and clarification, so that the agent does not refetch an unchanged roster unnecessarily.
37. As a maintainer, I want recognized local data failures reported without automatic network-style retries, so that missing or corrupt snapshots remain distinguishable from transient provider failures.
38. As a maintainer, I want unexpected programming errors to reject the run, so that a bug is not concealed by a generic success or service-unavailable message.
39. As a maintainer, I want failure classification to use the actual I/O boundary and error evidence, so that an arbitrary TypeError is not mislabeled as a temporary network error.
40. As a maintainer, I want error handlers to update only the failure outcome and necessary current-execution metadata, so that recovery cannot erase successful domain context.
41. As a maintainer, I want local structured events for retries and exhausted failures, so that I can see which operation failed, how many attempts ran, and how long it took.
42. As a project owner, I want logs to exclude prompts, raw roster contents, credentials, and unsanitized provider responses, so that diagnosing faults does not copy sensitive payloads into logs.
43. As a maintainer, I want interrupted runs to remain resumable while the process stays alive, so that the existing MemorySaver workflow remains useful.
44. As a project owner, I want process-restart recovery clearly excluded from this version, so that the project makes no durability claim that an in-memory checkpointer cannot provide.
45. As a maintainer, I want fault tests to use fake models, HTTP responses, and clocks through public interfaces, so that CI can verify failure behavior without external keys, delays, or quota consumption.
46. As a maintainer, I want all four supported workflows included in the failure matrix, so that fault tolerance is a project-wide property rather than a special case for team APIs.

## Implementation Decisions

- **Accepted architecture:** Follow ADR-0008 and the existing native StateGraph architecture. Use node retry policies, per-attempt timeouts, and typed error handlers for external boundaries. Keep task routing, identity resolution, ranking, and human clarification explicit; do not add a second general-purpose retry engine or a planner.
- **Policy ownership:** Policies may share cohesive configuration and classification helpers, but must be explicitly applied to the relevant boundaries. Do not enable a blanket graph-wide retry policy that also retries deterministic computations, expected domain outcomes, or human clarification.
- **Provider error contract:** Preserve enough safe error evidence to distinguish configuration/authentication failures, exhausted quota, short rate limits, recognized transport failures, upstream server failures, invalid payloads, cancellation, and unexpected code errors. HTTP status, provider error code, retry delay, and safe quota indicators must not be collapsed into one undifferentiated provider error.
- **Exception versus result:** Tagged transient provider failures must escape the relevant node as exceptions so native RetryPolicy can observe them. Permanent provider failures and domain outcomes remain structured results. Unexpected programming errors must not be relabeled as retryable provider failures.
- **Retry budget:** A logical external node activation is allowed at most three physical outbound requests, including its initial request. All native retries, provider/client retries, any short-rate-limit retry, and structured-output repair consume the appropriate shared budget. This is an upper bound, not an obligation to consume every remaining attempt. A cache hit makes no outbound request and consumes none.
- **No hidden multiplication:** Disable redundant SDK/caller retries or otherwise prove they consume the same budget. In particular, default model-client retries cannot execute underneath three graph attempts without accounting. Failed native attempts and a repair transition must not reset the logical activation's remaining allowance.
- **Budget scope:** Budgets belong to the current execution and logical node activation, not to mutable process-global counters or successful conversation context. Separate threads are isolated. A later legitimate lookup model step receives its own external-attempt budget; the independent per-turn tool-execution cap still applies. Three requests is not a cap on all model calls across an entire multi-step turn.
- **Transient classification:** Retry recognized transport/network failures, upstream 5xx failures, and timeouts of external attempts. A TypeError thrown by arbitrary business code is not automatically a transport failure. Other HTTP client failures, invalid credentials, exhausted quota, malformed provider data, unsupported conditions, not-found outcomes, unresolved identity, missing FM profiles, and an empty team-position reference are not transient retries.
- **Backoff:** Use bounded exponential backoff with jitter for ordinary transient failures. Keep timing settings explicit and testable. Honor a valid rate-limit retry delay rather than retrying before it expires; if a delay cannot be honored within the configured bounded wait, return a rate-limit outcome without an early retry.
- **429 handling:** Automatic short-rate-limit recovery requires a valid provider retry delay and evidence that daily quota remains. Missing or ambiguous evidence does not authorize retry. Daily-quota exhaustion and provider insufficient-quota codes never retry, regardless of HTTP status. At most one retry caused by short throttling is allowed in a logical activation, and it consumes the same three-request budget as network and server retries.
- **External-attempt deadlines:** Cap each football-provider request attempt at 15 seconds and each model request attempt at 60 seconds. Start with run timeouts; idle/heartbeat timeouts are unnecessary for this version. Propagate attempt cancellation to the HTTP/model client and suppress late State updates. Retry waits occur between attempts; this spec does not introduce an additional whole-turn wall-clock deadline.
- **Cancellation:** Caller cancellation and LangGraph control-flow exceptions propagate as cancellation/control flow. They do not trigger retries, JSON repair, normal external-failure fallback, or additional tool calls. Distinguish an external-attempt timeout, which may be retryable within budget, from an explicit caller abort.
- **Structured request repair:** Apply one validation-guided repair only to recognized parsing/schema failures of the request-understanding model output. Supply the original request, relevant confirmed context, output contract, and safe validation feedback; do not silently invent or default to a task. Send at most one additional physical model request carrying this repair feedback, included in the maximum of three model requests. Any failure of that repair request, including a transport failure or another invalid structured output, terminates request understanding with a deterministic failure response. Unused budget must not restart extraction or retry the repair request.
- **Request-understanding exhaustion:** Represent failure before a valid task has been extracted without fabricating a player-lookup or recommendation task kind. Route directly to the appropriate terminal failure response. Do not execute a previous request, reuse its current-turn outcome as if it answered the new message, or modify its successful conversation context.
- **Model lookup and answer boundaries:** Apply transient-call recovery to the lookup model and all final model-generated explanations, including lookup follow-ups. Retrying a final explanation must not rerun successful identity/data work. After exhaustion, provide a deterministic, safe failure message while retaining the newest completed business result and earlier successful contexts.
- **Deterministic data workflows:** Comparison, FM player recommendation, team recommendation ranking, local identity resolution, local source reads, and clarification remain deterministic. Audit broad catches, including tool execution behavior, so only recognized provider/transport/parser/data-boundary failures become expected outcomes; unclassified bugs and violated invariants remain thrown errors.
- **Native node coverage:** Request understanding, each lookup model step, final answer generation, team search, and current-squad acquisition are external boundaries with the relevant retry/timeout/handler behavior. Roster identity mapping and local computations do not become retryable simply because they share a task node with a provider request.
- **Error handlers:** Use the JavaScript state-first handler contract with typed NodeError context. After allowed retry recovery is exhausted, recognized external failures produce a safe outcome and route to the existing answer/failure response boundary. Handler recovery must not overwrite Active lookup, Active comparison, Active recommendation, Active team recommendation, player aliases, or confirmed mappings. Unexpected programming exceptions are rethrown.
- **Startup configuration:** Invalid or missing required configuration detected while constructing the agent remains a clear, non-retried startup failure. Once a run has started, recognized provider/configuration failures follow the safe task-failure outcome contract rather than silently falling through to a previous request.
- **State publication:** Nodes continue to return typed State patches. An unsuccessful or expired attempt must not publish its partial patch. A later explanation failure does not undo earlier successful business nodes or their active contexts. Store only compact current-execution fault metadata when needed for correct routing/budget accounting; raw exceptions and operational logs do not belong in State.
- **Lookup Agent loop:** Permit at most three actual search tool executions for one user turn. Count individual executions, including calls batched into one model response and failed executions. Prevent a fourth execution before dispatch, return an explicit limit outcome, and preserve useful completed source results. Transport retries of a model request are not search tool executions. A new user turn resets this tool allowance.
- **Identity safety during recovery:** Retries, repair, loop-limit handling, and fallback retain confirmed source IDs and existing identity boundaries. They do not change data source, merge same-named people, remove unsupported hard constraints, or rank from an incompletely mapped Team roster snapshot.
- **Interrupt safety:** Human identity, team, FM-profile, position, age, role, and season clarifications continue to use interrupt and Command resume. Human waiting is not a timed external request and must not consume retry, repair, or lookup-tool budgets. Resume continues the current request and retains confirmed mappings.
- **Cache safety:** Preserve the seven-day successful current-squad cache. Do not cache failures or responses that arrive after their request has been aborted/expired. A valid GET that completed and populated the cache before a later local node failure need not be rolled back; checkpoint rollback is not a transaction over external effects or cache storage.
- **Recovery scope:** Keep MemorySaver and the existing thread_id model. Checkpoints and pending clarification remain usable only while the process and its saver remain alive. Do not claim process-crash durability or introduce a Store, application database, or persistent checkpointer.
- **No compensation workflow:** Current football-provider operations and FM/Understat reads are read-only. Saga compensation, external write rollback, and write idempotency infrastructure are unnecessary for this scope.
- **Structured local logs:** Emit retry, repair, timeout/terminal-failure, and exhausted-budget events through a local structured log sink. Include node, available run/thread identity, attempt number, safe error category, and elapsed duration; distinguish repair from transport retry and tool-loop exhaustion. Use an explicit unavailable value where runtime correlation IDs do not exist.
- **Log data boundary:** Do not log prompts, model output bodies, raw roster data, full State, source records, API keys, authorization headers, or unfiltered exception/provider payloads. Preserve program-error propagation without relying on unsafe raw payload logging. Logging failure must not recursively retry a business operation or replace its original failure.
- **Module and interface changes:** Evolve the existing graph construction options, API client, request extractor, model invocation boundaries, State outcome contract, and safe logging integration as necessary. Keep helpers cohesive and existing injection points usable. Preserve the repository's arrow-function, type-only type-definition, and bottom-of-file export conventions.

## Testing Decisions

- **Confirmed seams:** The user approved the compiled createAgent graph as the primary seam, using invoke, Command resume, and getState. The existing createApiFootballClient interface is the narrow secondary seam for provider HTTP parsing, 429 evidence, cancellation, and cache behavior. No new public node/helper seam is required.
- **Behavior-focused assertions:** Test messages, outcomes, selected identities, actual outbound request/tool execution counts, cancellation signals, successful contexts, cache hits, and sanitized emitted events. Do not test private helper call order, duplicate the production retry formula in assertions, or snapshot full State as a substitute for behavior.
- **Real extraction path:** For structured-output recovery, run the actual request-understanding extractor through the graph with a controllable structured fake model. Do not replace it with an injected extractor that skips the repair behavior being tested.
- **SDK request accounting:** Include an integration case using a real configured model client with a fake HTTP transport, observed through the graph seam, to prove client-level retries do not multiply physical requests beyond three. No real gateway, key, or model is used.
- **Ordinary recovery:** Cover recognized network failure and 5xx followed by success, and repeated transient failures exhausting exactly the configured budget. Assert source IDs, effective filters, and selected team remain unchanged through recovery.
- **Mixed budgets:** Cover network failure followed by malformed structured output and repair, and network failure followed by a short 429 and another server failure. Also cover an initially malformed response followed by a repair-request transport failure: terminate after those two requests without spending the unused slot on another repair or restarting extraction. Assert no more than three physical requests, no more than one validation-repair request, and no more than one throttling-caused retry, with fresh independent budgets in another thread/activation.
- **429 evidence:** Use fake headers/body for both delta-seconds and HTTP-date retry delays where supported, positive and exhausted quota, provider insufficient-quota codes, missing/invalid retry delay, and a delay that cannot be honored within the bounded wait. Assert no early retry and no retry of daily-quota exhaustion.
- **Permanent failures:** Cover missing credentials, authentication/client failures, malformed provider JSON, schema-invalid payloads, valid not-found/empty responses, unresolved identities, and unavailable local data. Assert no inappropriate provider retry or weakened domain condition.
- **Timeout and abort:** Use fake timers and transports/models that observe cancellation. Verify 15-second API and 60-second model attempt limits, bounded recovery when budget remains, no retry after caller abort, and no State update or cache insertion from deliberately late responses.
- **Request-understanding failure:** Start with a successful prior request, then fail model transport/repair in the next turn. Assert the new turn gets its own failure outcome, previous active contexts remain, and no old identity or data task executes.
- **Final-answer failure:** Complete lookup/comparison/player recommendation/team recommendation data work, then exhaust the explanation model. Assert a deterministic failure reply and preservation of that newly completed result; do not rerun the data tool as part of model recovery.
- **Lookup loop limits:** Simulate repeated search tool requests, multiple calls within one model response, and failed tool executions. Assert at most three executions, no fourth dispatch, an explicit limit response, a fresh allowance on the next user turn, and unchanged resolved source IDs.
- **Interrupt/resume:** Interrupt an ambiguous identity or roster mapping, advance fake time while awaiting the human, and resume with Command. Assert no retry/error handler is triggered by the interrupt, mappings survive, and a valid cached roster is not fetched again.
- **Error transparency:** Inject an unclassified TypeError/invariant error through relevant node/tool boundaries and assert run rejection rather than retry or a generic provider outcome. Also verify known data-boundary failures retain their expected structured outcomes.
- **Failure logging:** Spy on the local log sink and assert event category, node/run/thread correlation, attempt, and duration. Include secret-looking prompts, roster values, and provider payloads in fake failures and assert those values never appear in logs.
- **Isolation:** Every graph test uses its own MemorySaver instance; tests that intentionally compare thread isolation may share that instance only within the same test. Fake clocks, model queues, transports, and log sinks are isolated between tests.
- **Prior art:** Reuse the existing full-graph player and team workflow tests, exact-identity lookup tests, Command-based alias/roster clarification tests, successful-context preservation tests, request-extraction structured-model tests, and controlled-clock API client cache tests.
- **Execution:** CI uses deterministic fakes, temporary local data fixtures, and fake timing only. Run relevant targeted tests during implementation, regular typechecking, and the full suite/build/lint after completion; no external provider quota is required.

## Out of Scope

- Persistent checkpointers, application databases, Store, process-restart/crash recovery, distributed workers, or a new production deployment target.
- Saga compensation, payments/reservations, external writes, or generalized write-idempotency infrastructure.
- A new planner, general workflow engine, generic fallback-model router, new data provider, frontend, RAG, or changes to recommendation formulas and eligibility rules.
- Replacing expected identity/position/season clarification with automatic retries or model guesses.
- A new schema/evaluator for factual correctness of final free-text answers. This feature handles transport/format/execution faults; final-answer evidence validation remains separate work.
- Remote LangSmith/other observability-service integration, raw prompt/body logging, large logs in State, or a logging database.
- A new whole-turn time SLA, unlimited Retry-After waiting, unbounded JSON repair, or retries of all exceptions.
- General dependency upgrades or unrelated CI/package-manager changes already present in the workspace.

## Further Notes

- This spec synthesizes the confirmed fault-tolerance discussion and ADR-0008; it is an implementation target, not a claim that the existing graph already enforces these policies.
- The three-request budget is per logical external node activation, including retries/repair for that activation. The lookup Agent loop has a separate maximum of three search executions per user turn; a conversation or complete turn can legitimately contain several distinct external node activations.
- Current provider failures are ordinary returned values, configured model clients have their own caller retry behavior, and several local/task catches are broad. The implementation must address those boundaries rather than merely adding retryPolicy options to graph registrations.
- LangGraph error handlers use the JavaScript state-first contract with NodeError as the second parameter. RetryPolicy is opt-in and operates on exceptions; interrupt is control flow. Reference: [LangGraph fault tolerance](https://docs.langchain.com/oss/javascript/langgraph/fault-tolerance).
- Keep documentation and examples clear that only failed attempt writes are discarded and already completed business results remain; no claim is made that graph recovery reverses every prior node, cache insertion, or external side effect.
