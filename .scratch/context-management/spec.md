# TactiScout 上下文管理落地方案

Status: implementation updated behind the legacy default; five-arm local-model ablation is still pending

日期：2026-10-19。本文记录上下文管理的研究、设计与当前实现边界。新策略保持实验开关，默认不切换到未经实测的投影或摘要模式。

## 产品目标与约束

用户能用自然语言持续调查：补充或撤销条件、指代上一份名单、纠正球员身份、追问某条证据，Agent 仍能沿用正确要求并给出有依据的结果。上下文机制的收益用任务正确性、端到端等待和实际 token 验证，不能用“提示词短了”代替。

保留现有 LangGraph.js StateGraph、阶段编排、SQLite checkpointer、候选评估器、证据 Reviewer 和 SSE。遵循 ADR-0005、0010、0014：在 recruitment 能力边界内整合上下文组装，避免为此迁移 Agent 框架或创建通用记忆平台。

研究依据：[一手资料研究](../tactiscout-mvp/research/context-management-primary-sources-2026-10-19.md)。外部项目提供设计依据，不证明本项目收益。

## 1. 建立统一的上下文组装入口

在 `src/recruitment/` 内由一个上下文模块拥有模型输入视图；初始公开接口建议：

```ts
buildRecruitmentContext(input): {
  messages;
  responseSchema;
  outputBudget;
  manifest;
}
```

输入是当前案件的只读视图、调用职责/阶段、可用动作、来源能力和模型预算。输出是完整待发请求与诊断清单。它不调用模型、不联网、不修改 State，也不重新实现候选资格或指标算法。

保留两种已有模型职责：需求理解 `understand`，以及 Planner 的 investigate/expand/expand_recovery/reorient/conclude。两者使用各自领域输入，但共享预算计数、优先级与序列化规则。身份名称变体等其他模型调用至少共享预算和用量观测，避免把 Planner 用量误称为全应用用量。

需求理解、Planner、导航摘要和球员名称变体模型入口都经过同一请求预算检查；身份变体模型失败也会记录估算输入 token。manifest 保存请求阶段、字节数、估算方法、输入/输出预算、窗口与省略计数，并包含 prompt、schema、payload 与案件 revision 的隐私安全指纹；当前尚未把所有调用的 manifest 持久化。默认不打印用户原话、网页全文或密钥。

确定性策略和 Reviewer 继续读取完整权威 State；模型上下文的压缩结果不回流覆盖它们。

## 2. 按职责投影，事实从 State 读取一次

| 调用职责 | 每次提供的必要内容 | 按需提供的内容 |
| --- | --- | --- |
| understand | 最新用户原话、上版 brief、正在回答的具体问题、用户实际看到的候选顺序与 ID | 最近完整问答、与新修改相关的旧原话 |
| investigate | 当前 brief、参考身份及其确认依据、来源能力、尚缺什么、最新工具观察与已完成动作索引 | 当前查询相关的候选详情、球队背景、报告片段 |
| expand/recovery | 当前硬条件、精确游标与筛选、能力覆盖、已评估/未评估/未查报告人数、失败状态 | 最近用户回答、最近一条策略拒绝原因 |
| reorient | 已查过的范围和结果、仍需满足的条件、证据缺口、剩余预算 | 与改变调查方向相关的旧步骤 |
| conclude | 全体当前有资格的已评估候选的精简目录、相关指标与样本、报告引用、未知与反证、比较覆盖 | 具体候选的长报告原文或历史详情 |

当前 brief、确认身份、位置证据、候选资格与分页观察已有明确所有者，不再要求模型从历史叙述重建。工具动作历史主要保留“做了什么、成功/零结果/失败、产生哪些 ref、下一步是否可做”，避免重复携带完整数据。

projection 模式按最近 3 个用户回合保留完整问答：当前最新发言单独作为 `message`，历史投影包含较早用户发言，以及与保留回答对应的助手追问；旧的受保护原话只通过精确引用及其 event ID 提供，不会混入近期对话。legacy 臂继续使用原有完整用户消息列表，便于配对比较。字段取值来自现有状态，不能把旧工具摘要的“0”覆盖当前未知状态。

需求解析器看到的旧消息可减少，但 `validateRecruitmentBrief` 核验用户引文时仍能访问原始消息档案。二者的输入不能再混用。新增稳定 turn/event ID，原话引用可指向对应记录；旧 checkpoint 缺 ID 时按既有顺序生成兼容映射，不改写原话。

## 3. 工具结果提供证据包与可读取引用

每份证据包最少包括：类型、所属案件及 scope revision、来源原生 ID、数据快照/内容版本、涉及球员与指标、可直接支持的内容、缺口或冲突、来源与时间范围、是否还有未提供内容。

数值证据保留指标键、数值、单位、basis、赛事/赛季、样本和必要定义；共享元数据只出现一次。文本证据优先选取包含判断及其限定语的完整片段，保留 source/ref 和范围，明确只是摘录；不能把“前 900 字符”作为唯一策略。未提供全文不等于全文没有其他信息。

首期复用 State 中的 `evaluatedPlayers`、`retrievedKnowledge`、Understat research 与现有来源快照。追加只读动作 `read_case_evidence({refs, fields, cursor?, limit})` 读取已取得资料；不重新抓网，也不重新计算评分。它只能访问当前案件已登记 ref，拒绝任意文件路径、跨案 ID、过期 scope revision 和未知 ref。同一案件、相同有效需求范围及相同证据内容下，ref 可跨普通追问继续使用；更改需求范围后旧 ref 返回 stale。历史 checkpoint 中旧格式 ref 返回 stale。被引用版本不可用时不能悄悄换成最新网页。

默认每轮最多 2 次定向读取，每次受 token 预算和分页上限控制，计入原有总决策/工具预算。该数值属于初始实验参数。需要原文的结论阶段允许受限 read，然后返回 Planner；要同步修改该阶段 schema、可用动作和策略，保留 ask/finish 的原约束，不因此开放任意新搜索。

模型所有引用仍经现有服务端白名单与 Reviewer 校验。ref 的存在不表示资料被模型读过；输出只能引用已提供的证据片段或现有可核验的结构化指标。

候选目录不能为省 token 静默只保留前 N 名。先保留当前有资格的已评估候选的完整精简目录、每名候选关键依据/缺口与总计数；长篇证据按 ref 读取。只有候选目录及其候选 ID 约束 schema 本身造成硬窗口溢出，且移除候选数据和候选 ID 枚举后的同一请求可以放入窗口时，才将完整候选池平均分成不超过 5 批；每个候选只进入一批，每批最多选择 1 名有直接指标支持的考察线索。批次只允许完成比较，不能用局部候选集追问用户或提前结束。输出明确显示各批次覆盖，批次之间不声称统一排序；某批最小上下文仍放不下时安全返回容量错误，不能静默省略或让模型自行截断。

## 4. 请求前预算与渐进降载

预算覆盖 system、阶段/来源指令、响应 schema 或 function schema、格式开销、案件状态、历史、检索证据，并为输出和误差留空间。

```text
inputLimit = min(providerInputLimit,
                 verifiedContextWindow - reservedOutput - safetyMargin)
```

供应商若独立限制输入和总窗口，分别遵守。兼容接口暴露的字段要实测，不能从返回 usage 缺失推断 token 为零。

在仓库 16K profile 下，目前 understanding/investigate/reorient 继续使用原来的通用 8192 输出上限，expand 继续使用原来的 1024 上限；只为受限且最复杂的 conclude 报告新增默认 4096 上限，并由实际 wire 请求与对应 manifest 共用该值。这个结论上限仍是待真实模型完整报告验证的起始值；若 structured output 达到上限，再调整分配，而非截断 JSON。安全余量继续为 1024。尚未用证据支持普通调用降到 3072/2048，后续先观察它们的实际输出和用量。

精确 tokenizer/服务端计数可用时使用它；否则使用注明估算性质的模型适配计数器，并按实际 usage 校准保守余量。OpenAI tokenizer 不能直接当作 Qwen 精确计数器。实际运行窗口未知时保留诊断状态并要求部署配置给出可信上限，不能把宣传窗口当运行窗口。

降载顺序：去重和字段投影 → 省略过期过程记录 → 长证据换可读取 ref → 相关片段选择 → 旧动态轨迹摘要 → 必要目录分批。结论分批只在候选目录与候选 ID schema 导致超窗、而候选数据和候选 ID schema 同时移除后其余请求可放入窗口时启用；无关的历史或其他 payload 超窗不能借分批绕过。每批独立选一条线索，报告明确不具备跨批排序。若证据读取次数已耗尽，所有已经读出的原文、报告和方法证据都必须保留；压缩后仍超窗时返回可恢复容量错误。系统指令、当前原话、有效硬条件、未解决问题、确认身份、准确游标和引用所需单位/样本不可静默删除。

设置低于硬上限的软目标来控制本机延迟，初始以 6–8K 输入作为实验范围，最终由本机分布决定。软目标不是正确性硬门槛，不为满足它牺牲必要事实。

若连最小必要上下文都放不下，返回可恢复的容量状态并保留案件；向用户说明当前进度与可继续的分批范围，不能让 provider 隐式截断，也不能把容量问题说成没有候选。

## 5. 按需生成版本化案件摘要

摘要只负责旧对话导航：概括早期用户消息与助手追问，用于帮助 Planner 识别案件目标如何变化。当前实现不总结球员事实、调查动作完成状态或证据 ref；身份、硬条件、指标和资格从 State 直接投影，不能由摘要决定。

当前实验触发使用保守启发式：至少 12 轮用户消息、尚未摘要的较早对话估算至少 2,048 token，且存在可摘要事件。它没有精确测量 Planner 完整请求是否仍超过软目标，也不能证明旧对话是主要超量来源；因此摘要只在显式 `summarized` 实验模式运行，不能据此宣称节省上下文或延迟。后续只有实验表明确有收益时，才值得把摘要升级成自动降载机制。正常短任务不调用摘要模型。

通过显式 `compact_case_context` 图节点执行：模型调用前检查需要压缩 → 生成并验证 → checkpoint 保存 summary → 重新组装 → 原阶段继续。压缩节点不计为 Planner 选择动作，但有独立调用/耗时/失败计数与有限预算，不能形成压缩循环。摘要模型也必须满足同样的来源处理权限与部署地址约束。

摘要记录版本、覆盖用户轮次和实际引用的事件 ID。生成时仍要求模型按顺序返回该批次完整事件账本以校验输入覆盖，但账本只用于当前请求，不持久化或传给 Planner；这样 checkpoint 不会随着对话轮数积累无界 ID 列表。摘要文本保留不超过 2,000 字符的逐字摘录。每次用户改条件、换参考球员或拒绝身份后，摘要仍只是低信任历史导航，旧决定不得成为当前限制。

摘要生成后当前校验输出长度、事件 ID 覆盖顺序，以及每条摘录是否为来源事件中的连续原文；它不具备语义事实核验，因此 prompt 禁止它声称调查动作已完成或复述证据。验证器不能保证自由叙述完全准确，摘要只作导航，不是推荐证据。失败时案件仍以结构化 brief 与原始 history 为准。

## 6. 持久化、缓存与长期记忆

完整案件状态和原始历史继续由 SQLite checkpointer 保存；请求投影不删历史。它是同一球探案件的持久工作状态，不是跨案件的用户画像。新的 summary 为可选 State 字段，旧 checkpoint 默认无摘要；ref 绑定案件、需求范围指纹和证据内容版本，恢复后重新检查。取消、重启和旧 checkpoint 恢复仍遵守既有生命周期。

system 的稳定规则放前面，阶段与数据放后面；固定字段顺序和 schema 版本，减少无意义变化。候选 ID 与证据白名单继续动态约束，不为提高缓存命中而放松。记录实际支持的 cache usage；Ollama prefill/cache 数据不等同于 Claude 的计费缓存。收益没有实测前不声称“缓存已优化”。

持久状态按所有权分为三个已有/可选范围：SQLite checkpoint 保存案件原始历史和结构化进度；共享知识库保存可复用的足球资料、指标方法与带来源的身份映射；跨案件用户偏好只有用户明确选择“设为以后默认”后才保存来源与更新时间。当前案件明确要求优先于默认值，一次案件的年龄、预算、球队和球员不自动跨案继承。

不把对话自动提炼成预测用户下一步需求的画像，也不在首期实现情景/语义/程序记忆三套存储、记忆重要性衰减或聚类压缩。球探案件中的用户修正和被撤销条件需要可追溯；原始事件与当前权威 brief 保持可核验，导航摘要只能辅助恢复上下文。只有出现明确的跨案件默认偏好需求后，再做显式保存、查看和清除入口；单机可用浏览器存储，多用户/跨设备再采用稳定 user ID 对应的 Store namespace。足球知识库、身份映射与用户偏好维持各自范围。

程序规则仍按代码/配置版本发布并经过 Harness。网页正文和摘要无权写系统规则、确认身份或新增用户偏好；外部文本作为低信任证据传入，不能因为被摘要就升级为可信控制信息。

## 7. 代码归属与实施顺序

遵循模块化单体，不先创建跨应用通用 memory framework。建议上下文职责由少量深模块承载：

```text
src/recruitment/
  context.ts                 统一入口、各职责投影、预算与 manifest
  case-evidence.ts           已取得证据的 ref 注册/校验和有界读取
  case-summary.ts            摘要合同、生成、更新与验证
  planner-context.ts         迁移期兼容入口，调用方迁完后合并/删除
  conversation/
    planning-node.ts         调用统一入口，保留规划/策略职责
    understanding-node.ts    拆开模型近期消息与验证用原话档案
    state.ts                 仅增加无法推导的 revision/summary 数据
```

这是一份责任划分，不是必须新增同等数量文件的要求；若接口足够小可合并。纯预算函数最初留在上下文模块，只有确实有独立复用和复杂度时再拆。

第一批：采集完整请求 manifest，冻结基线；统一理解与 Planner 的请求组装；合并现有投影、去重，接入预算；补齐用户原话档案访问。

第二批：证据包、ref 与 read_case_evidence；联动所有受影响阶段的 schema、动作预算和 Reviewer；消除固定字符前缀作为唯一正文策略。

第三批：按需摘要图节点、checkpoint 兼容和失败恢复；长对话场景验证。明确偏好的保存入口作为独立产品任务，避免与主链改造互相阻塞。

每批都可通过同一实验开关恢复旧请求投影；读取权限、硬条件、来源模型处理约束、证据 Reviewer 始终启用。

## 8. 核心机制必须通过消融

新增现有 CLI 的 `--compare-context-management` 模式，沿用 `pnpm eval:local-agent`，复用真实 `createRecruitmentConversation` 整图；不新建一套 Agent 评测器。

| 实验臂 | 内容 | 因果比较 |
| --- | --- | --- |
| `legacy` | 保留既有历史筛选策略；其余请求通过同一预算与观测入口 | 基线 |
| `projection` | 只开启近期对话投影、稳定事件 ID 和受保护原话引用 | 对比 legacy，检验历史投影 |
| `evidence` | 只开启案件证据目录与受限按需读取，保留 legacy 历史策略 | 对比 legacy，检验证据引用读取 |
| `unified` | 同时开启 projection 和 evidence，不调用摘要模型 | 对比两个单项臂，检验组合及交互效果 |
| `summarized` | 在 unified 上增加经过逐字来源校验的旧对话导航摘录 | 对比 unified，检验摘要的增量价值 |

这些是五种真实整图运行模式，不是仅改变报告标签。证据读取采取显式 ref、字段与游标分段；本方案不再增加第二套模型摘要或语义选句系统，避免与现有知识检索重复。必要事实校验不在产品中关闭；若研究“去掉直接条件注入”，只在隔离的非产品评测配置运行，并禁止产生可执行外部动作。

固定模型/运行配置、来源快照、初始案件、对话脚本、工具预算和权限；五臂按起始顺序轮换，五轮内每种策略各处于每个执行位置一次，同一机器串行跑模型。至少 5 轮；结果不稳定就扩大样本。不要用 5 次实测宣称总体 p95；报告原始值、中位数、范围与失败次数。模型故障、超限与摘要失败均保留在结果中。

公开验证边界：buildRecruitmentContext 输入输出合同；createRecruitmentConversation 的完整对话；现有 Harness CLI；真实兼容接口 wire 请求（system/schema/messages/stream/output limit）。验证器继续读取原始 State，不以模型自己的解释当判定真值。

## 9. 用户看到的变化

用户修改要求后，案件立即显示新的有效条件；对过去已回答的问题减少重复追问。资料较多且确实进入分批步骤时，SSE 展示“正在分批比较候选”或“正在核对相关报告原文”，不显示 tokenizer、压缩比例、内部 schema 或模型隐藏推理。普通短请求应直接前进；长案件可以继续原调查，报告清楚表示实际比较范围。

## 当前交付与验证边界

已在招聘模块内落地统一请求组装与预算观测、包含组件字节和版本指纹的隐私安全上下文清单、Provider 实际 token 用量状态、稳定案件事件 ID、Planner 历史投影、案件证据目录和受限读取，以及现有 Harness 的五臂长对话消融入口。摘要模型只能挑选旧对话中的逐字片段；程序验证事件 ID、片段存在、严格顺序和长度后，才形成导航摘录。完整覆盖账本只在验证时使用，checkpoint 与 Planner 只携带有界摘录、引用 ID 和覆盖轮次。摘录仍可能遗漏有用信息，因此它不是当前需求、球员事实或推荐证据；权威 brief、指标和资格仍来自结构化状态与 Reviewer。旧 checkpoint 的自由文本摘要不会再被当作已核验摘录传给 Planner。

本轮新增结论投影：从案件 State 为所有符合当前范围的已评估候选构造完整目录，只携带需求相关且实际观测到的指标、样本、单位及可用百分位；未知值保持缺席，显式零值保留。projection/unified/summarized 的结论上下文因此不再重放旧候选搜索页和多批评估结果；所有原始记录仍在 LangGraph State/checkpoint。若结论请求仍超过已验证窗口，且移除候选数据与响应 schema 中的候选 ID 枚举后其余请求能够适配，则 Planner 使用完整 State 候选目录构造最多 5 个平衡批次；每批 schema 只允许 finish，防止局部候选池触发追问并中断后续批次。每个批次只从自己的完整候选切片中输出一名线索，最后报告批次数、逐批覆盖人数和有无直接证据线索，并明确没有跨批统一排名。无关用户背景导致的超窗不会触发候选分批；单批仍放不下时返回容量错误。读取预算耗尽时，各批仍保留已读原文。整 Planner HTTP 模拟覆盖候选全覆盖、候选 ID schema 过大但分批可容纳、非候选上下文仍超限时拒绝分批；独立 schema 测试验证批次拒绝 ask_user。尚未通过真实模型实验验证选择质量或延迟。

`legacy` 仍为默认策略。`projection`、`evidence`、`unified` 与 `summarized` 仅在显式 Harness 选项下运行。CLI 固定 Barcelona U23 中场 curated 场景和 20 条范围保持压力消息，报告各臂候选顺序、证据顺序、通过率、各阶段上下文 token/字节清单、Provider 实际用量、摘要调用与端到端耗时。压力脚本用于增加历史长度，不等同于自然用户对话分布。测试句使用明确且可连续引用的能力描述，避免评测被不相关的转述引文错误提前终止。

实现验证包含上下文组装纯函数、Planner 本机 HTTP 请求预算兜底、超窗结论分批、完整 LangGraph 候选与证据投影行为、逐字摘要验证、Harness CLI 和五臂轮换入口。新增聚焦测试验证每名合格候选均保留、只传请求指标、缺失与显式 0 区分、读取预算耗尽时证据不丢、追问/短名单/证据被保留、重复搜索/评估流水被移除。实际 Ollama preflight 和完整五臂仍待重跑；此前五臂失败结果发生在 `legacy` 模式，不能归因于新上下文策略，也不能证明它们有效或无效。摘要触发仍基于旧对话长度启发式，不能据此称为 token 压缩或延迟优化。实际消融达成第 8 节登记的正确性与收益门槛之前，维持 `legacy` 默认。

2026-10-19 的实现前真实运行诊断进一步区分了两个问题：一轮 `unified` 整图请求中，understand 请求为 12,371 bytes、估算 4,751 tokens，Provider 返回的该次 prompt usage 为 1,475 tokens；这个单样本可能受结构化输出 schema 计数口径影响，不能据此直接校准估算比例。后续 expand Planner 请求为 15,881 bytes、估算 6,096 tokens，在 60 秒时限失败；这是本机模型推理延迟问题，随后按既有确定性扩页回退继续。旧版本结论请求为 42,572 bytes、估算 16,328 tokens；结论历史降载已触发，但在当时 16K 窗口、8,192 输出预留和 1,024 安全余量下仍被挡在模型调用之前。它说明旧结论视图或预算边界需要处理，不能说“摘要已经解决超窗”，也不能把 Planner 超时归因于上下文压缩。

实现已针对①减少结论目录中的重复字段、按需读取证据，并在必要时完整分批；针对②增加独立结论模型输出上限（默认 4,096 tokens），与请求 manifest 的预算共用同一设置。聚焦回归覆盖了 wire 请求、输入预算和批次候选覆盖。③仍未解决：Ollama 官方 API 文档公开最终响应的 `prompt_eval_count`，但不能据此声称存在可用的请求前 tokenizer 计数 API；仍需积累多种中文/JSON/schema 请求样本，不能用单次 usage 比值改写 16K 硬窗口规则。[Ollama API](https://github.com/ollama/ollama/blob/main/docs/api.md#generate-a-completion)

消融状态分成两次记录：早期一次实验在 `legacy` 的 expand Planner 阶段约 60 秒超时，没有进入 20 轮脚本，不能比较上下文策略；最近一次按五臂、每臂五轮运行的命令持续超过 25 分钟，因没有逐轮进度而人工中止。后者也没有有效结果。现有自动测试和本机 HTTP 模拟证明请求构造与保护规则，不证明真实模型的任务正确性、用量节省或延迟收益。因此保持 `legacy` 默认；正式消融仍待建立可观察进度、先通过短任务预检后再运行完整配对实验。

后续请求投影审查发现扩页 Planner 的 `caseProgress` 还重复携带了工具预算计数、保护引文索引、完整证据目录和整轮候选页列表；其中剩余工具动作已由 `availableActions` 表示，确切筛选和下一页游标也由 `expansionConstraints` 表示。现在扩页与扩页恢复阶段只传已发现候选数和最新候选页观察；历史裁剪计数继续进入隐私安全 manifest，但不进入模型提示词。真实 API wire 回归验证：模型仍收到最新页、已发现数量和候选总评估数，旧页、证据目录、引文原文及重复预算信息已移除。该改动尚未证明本机模型延迟改善；需在重新运行的五臂实验中观察。
