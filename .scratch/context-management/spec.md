# TactiScout 上下文管理落地方案

Status: implemented behind the legacy default; long-running model ablation not yet executed

日期：2026-10-19。本文记录上下文管理的研究、设计与当前实现边界。新策略保持实验开关，默认不切换到未经实测的投影或摘要模式。

## 产品目标与约束

用户能用自然语言持续调查：补充或撤销条件、指代上一份名单、纠正球员身份、追问某条证据，Agent 仍能沿用正确要求并给出有依据的结果。上下文机制的收益用任务正确性、端到端等待和实际 token 验证，不能用“提示词短了”代替。

保留现有 LangGraph.js StateGraph、阶段编排、SQLite checkpointer、候选评估器、证据 Reviewer 和 SSE。遵循 ADR-0005、0010、0014：在 recruitment 能力边界内整合上下文组装，避免为此迁移 Agent 框架或创建通用记忆平台。

研究依据：[一手资料研究](../tactiscout-mvp/research/context-management-primary-sources-2026-10-19.md)。外部项目提供设计依据，不证明本项目收益。

## 当前实现与具体问题

| 位置 | 代码事实 | 影响与待验证假设 |
| --- | --- | --- |
| `src/recruitment/conversation/state.ts` | history 追加保存；brief、候选、评估、位置证据、检索资料、游标另有结构化字段 | 已有足够事实基础；多处内容又进入历史，造成重复与旧信息竞争的可能 |

| `src/recruitment/recruitment-planner.ts` | contextChars 统计序列化案件长度；system、schema 和 context 分别构造；服务端 token 有独立归一化 | 缺少完整请求的分类体积与调用前预算；字符数不等于 token |

以上为静态代码审计，不据此断言所有等待都由输入过长造成。前序延迟报告已有反例：输出长度、图路径、模型预热、并发和 streaming 都可能影响耗时。

## 1. 建立统一的上下文组装入口

在 `src/recruitment/` 内由一个上下文模块拥有模型输入视图；初始公开接口建议：

```ts
buildRecruitmentContext(input): {
  messages;
  responseSchema;
  outputBudget;
  manifest;
}
```

输入是当前案件的只读视图、调用职责/阶段、可用动作、来源能力和模型预算。输出是完整待发请求与诊断清单。它不调用模型、不联网、不修改 State，也不重新实现候选资格或指标算法。

保留两种已有模型职责：需求理解 `understand`，以及 Planner 的 investigate/expand/expand_recovery/reorient/conclude。两者使用各自领域输入，但共享预算计数、优先级与序列化规则。身份名称变体等其他模型调用至少共享预算和用量观测，避免把 Planner 用量误称为全应用用量。

所有模型入口都先经过请求预算检查；先输出 observe-only 清单，不改实际请求，以得到基线。manifest 保存 prompt/schema 版本、案件 revision、各类 token 估算、保留/省略范围、证据 ref、计数方式与实际 usage；默认不打印用户原话、网页全文或密钥。

确定性策略和 Reviewer 继续读取完整权威 State；模型上下文的压缩结果不回流覆盖它们。

## 2. 按职责投影，事实从 State 读取一次

| 调用职责 | 每次提供的必要内容 | 按需提供的内容 |
| --- | --- | --- |
| understand | 最新用户原话、上版 brief、正在回答的具体问题、用户实际看到的候选顺序与 ID | 最近完整问答、与新修改相关的旧原话 |
| investigate | 当前 brief、参考身份及其确认依据、来源能力、尚缺什么、最新工具观察与已完成动作索引 | 当前查询相关的候选详情、球队背景、报告片段 |
| expand/recovery | 当前硬条件、精确游标与筛选、能力覆盖、已评估/未评估/未查报告人数、失败状态 | 最近用户回答、最近一条策略拒绝原因 |
| reorient | 已查过的范围和结果、仍需满足的条件、证据缺口、剩余预算 | 与改变调查方向相关的旧步骤 |
| conclude | 全体当前有资格的已评估候选的精简目录、相关指标与样本、报告引用、未知与反证、比较覆盖 | 具体候选的长报告原文或历史详情 |

当前 brief、确认身份、位置证据、候选资格与分页观察已有明确所有者，不再要求模型从历史叙述重建。工具动作历史主要保留“做了什么、成功/零结果/失败、产生哪些 ref、下一步是否可做”，避免重复携带完整数据。

最近对话按完整问答保留，初始以最近 3 组作为实验参数；正在等待的问题与回答、最新原话和被引用的旧原话不受普通近期窗口裁剪。字段取值来自现有状态，不能把旧工具摘要的“0”覆盖当前未知状态。

需求解析器看到的旧消息可减少，但 `validateRecruitmentBrief` 核验用户引文时仍能访问原始消息档案。二者的输入不能再混用。新增稳定 turn/event ID，原话引用可指向对应记录；旧 checkpoint 缺 ID 时按既有顺序生成兼容映射，不改写原话。

## 3. 工具结果提供证据包与可读取引用

每份证据包最少包括：类型、所属案件及 scope revision、来源原生 ID、数据快照/内容版本、涉及球员与指标、可直接支持的内容、缺口或冲突、来源与时间范围、是否还有未提供内容。

数值证据保留指标键、数值、单位、basis、赛事/赛季、样本和必要定义；共享元数据只出现一次。文本证据优先选取包含判断及其限定语的完整片段，保留 source/ref 和范围，明确只是摘录；不能把“前 900 字符”作为唯一策略。未提供全文不等于全文没有其他信息。

首期复用 State 中的 `evaluatedPlayers`、`retrievedKnowledge`、Understat research 与现有来源快照。追加只读动作 `read_case_evidence({refs, fields, cursor?, limit})` 读取已取得资料；不重新抓网，也不重新计算评分。它只能访问当前案件已登记 ref，拒绝任意文件路径、跨案 ID、过期 revision 和未知 ref。被引用版本不可用时返回明确 stale/missing，不能悄悄换成最新网页。

默认每轮最多 2 次定向读取，每次受 token 预算和分页上限控制，计入原有总决策/工具预算。该数值属于初始实验参数。需要原文的结论阶段允许受限 read，然后返回 Planner；要同步修改该阶段 schema、可用动作和策略，保留 ask/finish 的原约束，不因此开放任意新搜索。

模型所有引用仍经现有服务端白名单与 Reviewer 校验。ref 的存在不表示资料被模型读过；输出只能引用已提供的证据片段或现有可核验的结构化指标。

候选目录不能为省 token 静默只保留前 N 名。保留当前有资格的已评估候选的完整精简目录、每名候选关键依据/缺口与总计数；详细证据分批读取。必要目录本身也超预算时，转为有记录的分批比较并保留每批覆盖；只能交付实际比较过的范围，不声称全池已经比较。

## 4. 请求前预算与渐进降载

预算覆盖 system、阶段/来源指令、响应 schema 或 function schema、格式开销、案件状态、历史、检索证据，并为输出和误差留空间。

```text
inputLimit = min(providerInputLimit,
                 verifiedContextWindow - reservedOutput - safetyMargin)
```

供应商若独立限制输入和总窗口，分别遵守。兼容接口暴露的字段要实测，不能从返回 usage 缺失推断 token 为零。

在仓库 16K profile 下，以下只是待验证的起始保留值，不在本次直接改配置：understand 输出 3072，investigate/reorient 2048，expand 1024，conclude 4096；安全余量先取 1024。需要用最复杂合法需求/完整报告校准，若 structured output 达到上限，则重新调整分配，而非截断 JSON。优先观测为何当前普通调用需要 8192，再决定降低输出上限。

精确 tokenizer/服务端计数可用时使用它；否则使用注明估算性质的模型适配计数器，并按实际 usage 校准保守余量。OpenAI tokenizer 不能直接当作 Qwen 精确计数器。实际运行窗口未知时保留诊断状态并要求部署配置给出可信上限，不能把宣传窗口当运行窗口。

降载顺序：去重和字段投影 → 省略过期过程记录 → 长证据换可读取 ref → 相关片段选择 → 旧动态轨迹摘要 → 必要证据分批。系统指令、当前原话、有效硬条件、未解决问题、确认身份、准确游标和引用所需单位/样本不可静默删除。

设置低于硬上限的软目标来控制本机延迟，初始以 6–8K 输入作为实验范围，最终由本机分布决定。软目标不是正确性硬门槛，不为满足它牺牲必要事实。

若连最小必要上下文都放不下，返回可恢复的容量状态并保留案件；向用户说明当前进度与可继续的分批范围，不能让 provider 隐式截断，也不能把容量问题说成没有候选。

## 5. 按需生成版本化案件摘要

摘要只负责旧对话与调查进展：目标演变、已做决策及原因、用户已回答的问题、尚未解决的事项、接下来可做什么，以及原始事件/证据 ref。身份、硬条件、指标和资格从 State 直接投影，不能由摘要决定。

触发条件同时满足：确定性投影后仍超过软目标；主要超量来自可压缩的旧动态轨迹；预期压缩能腾出有意义空间。正常短任务不额外调用摘要模型。若超量来自必要候选指标或 schema，优先处理相应数据布局，不对它们做自由文字总结。

通过显式 `compact_case_context` 图节点执行：模型调用前检查需要压缩 → 生成并验证 → checkpoint 保存 summary → 重新组装 → 原阶段继续。压缩节点不计为 Planner 选择动作，但有独立调用/耗时/失败计数与有限预算，不能形成压缩循环。摘要模型也必须满足同样的来源处理权限与部署地址约束。

摘要记录 version、sourceEventRange、未覆盖范围、briefRevision、数据版本、token 数与生成器版本。优先增量记录有事件 ID 的决策，必要时从原始记录重建，避免只反复“摘要旧摘要”。每次用户改条件、换参考球员或拒绝身份后重新校验摘要中的关联，旧决定可以保留为历史，不得继续成为当前限制。

摘要生成后校验原话引用、身份和证据 ref 可解析，所声称已完成步骤确有观察，未解决事项未丢失；验证不能保证自由叙述全部正确，因此摘要只作导航，不是推荐证据。失败回退到结构化事实、原始相关轮次和明确有限的调查进展。

## 6. 持久化、缓存与长期记忆

完整案件状态和原始历史继续由 SQLite checkpointer 保存；请求投影不删历史。新的 summary 为可选 State 字段，旧 checkpoint 默认无摘要；ref 和 manifest 绑定案件/scope revision，恢复后重新检查。取消、重启和旧 checkpoint 恢复仍遵守既有生命周期。

system 的稳定规则放前面，阶段与数据放后面；固定字段顺序和 schema 版本，减少无意义变化。候选 ID 与证据白名单继续动态约束，不为提高缓存命中而放松。记录实际支持的 cache usage；Ollama prefill/cache 数据不等同于 Claude 的计费缓存。收益没有实测前不声称“缓存已优化”。

长期记忆的产品入口是“将此偏好设为以后默认”，保存明确偏好、来源与更新时间；当前案件明确要求优先于默认值。一次案件的年龄/预算/球队不自动跨案继承。单机原型可以复用已有浏览器偏好存储；要跨设备或多用户时，再用稳定 user ID 与 server Store namespace。足球知识库、身份映射与用户偏好维持各自范围。

程序规则仍按代码/配置版本发布并经过 Harness。网页正文和摘要无权写系统规则、确认身份或新增用户偏好；外部文本作为低信任证据传入，不能因为被摘要就升级为可信控制信息。

## 7. 代码归属与实施顺序

遵循模块化单体，不先创建跨应用通用 memory framework。建议上下文职责由少量深模块承载：

```text
src/recruitment/
  context.ts                 统一入口、各职责投影、预算与 manifest
  case-evidence.ts           已取得证据的 ref 注册/校验和有界读取
  case-summary.ts            摘要合同、生成、更新与验证
  planner-context.ts         迁移期兼容入口，调用方迁完后合并/删除
  conversation/
    planning-node.ts         调用统一入口，保留规划/策略职责
    understanding-node.ts    拆开模型近期消息与验证用原话档案
    state.ts                 仅增加无法推导的 revision/summary 数据
```

这是一份责任划分，不是必须新增同等数量文件的要求；若接口足够小可合并。纯预算函数最初留在上下文模块，只有确实有独立复用和复杂度时再拆。

第一批：采集完整请求 manifest，冻结基线；统一理解与 Planner 的请求组装；合并现有投影、去重，接入预算；补齐用户原话档案访问。

第二批：证据包、ref 与 read_case_evidence；联动所有受影响阶段的 schema、动作预算和 Reviewer；消除固定字符前缀作为唯一正文策略。

第三批：按需摘要图节点、checkpoint 兼容和失败恢复；长对话场景验证。明确偏好的保存入口作为独立产品任务，避免与主链改造互相阻塞。

每批都可通过同一实验开关恢复旧请求投影；读取权限、硬条件、来源模型处理约束、证据 Reviewer 始终启用。

## 8. 核心机制必须通过消融

新增现有 CLI 的 `--compare-context-management` 模式，沿用 `pnpm eval:local-agent`，复用真实 `createRecruitmentConversation` 整图；不新建一套 Agent 评测器。

| 实验臂 | 内容 | 要回答的问题 |
| --- | --- | --- |
| A | 当前阶段裁剪，保持现有来源指令、schema 和 policy | 当前基线如何 |
| B | 统一投影、去重、预算、证据包与可读取 ref；无 LLM 摘要 | 确定性上下文组织是否已解决主要问题 |
| C | B + 按需摘要 | 摘要的收益是否覆盖额外调用、延迟与信息损失 |

先对 B 的变化做逐项单请求配对：去重/投影、文本片段选择、ref 读取分别开关，避免把多个优化混成单一因果。整图三臂检验综合产品效果。必要事实校验不在产品中关闭；若研究“去掉直接条件注入”，只在隔离的非产品评测配置运行，并禁止产生可执行外部动作。

固定模型/运行配置、来源快照、初始案件、对话脚本、工具预算和权限；使用 AB/BA 交错顺序，区分冷/热运行，同一机器不并发跑模型。每个核心场景至少 5 对作为试验起点，结果不稳定就扩大样本。不要用 5 次实测宣称总体 p95；报告原始值、中位数、范围与失败次数。模型故障、超限与摘要失败均保留在结果中。

公开验证边界：buildRecruitmentContext 输入输出合同；createRecruitmentConversation 的完整对话；现有 Harness CLI；真实兼容接口 wire 请求（system/schema/messages/stream/output limit）。验证器继续读取原始 State，不以模型自己的解释当判定真值。

固定场景包括：

- 凯恩替代者，多轮增加/撤销年龄限制，参考本人始终排除。
- 巴萨后卫，要求出球与高位防守，保持当前指标可测/不可测边界。
- 基米希/切尔基中文名、外号、错字和同名消歧；用户否定身份后旧摘要不能复活被拒绝对象。
- CM、LB 等细分位置和多选位置，保持宽召回、精确资格、待核实状态与分页 nextOffset。
- “第三个更像谁”，对齐上一份实际可见顺序，不使用内部召回顺序。
- 20–30 轮积累、多批候选、早期约束修正、长报告反证在尾部、资料冲突与缺失值。
- 网页含伪指令、未知/过期/跨案件 ref、读取失败、摘要失败、重启和旧 checkpoint 恢复。

正确性必须守住：当前硬约束与更正、身份/本人排除、可见指代、精确游标、指标数值/单位/样本、未知不变零、报告引用存在、已读/未读范围不伪造。单独统计误差与未完成案件，不能通过少推荐几个人或减少调查范围假装优化成功。

效率统计包含需求理解、Planner、摘要及其他实际模型请求的输入/输出 token 与覆盖率，估算误差，工具/读取调用数，端到端延迟、首个有用进度延迟、超限/超时/恢复次数。兼容服务不报告 prefill/cache 时记 unknown，不从总耗时倒推。

工程验收门槛：固定关键正确性用例全部通过；真实配对中没有新增可复现的约束、身份或证据错误。初始收益目标为长上下文场景总输入 token 中位数减少至少 25%，短场景无额外摘要请求，端到端中位延迟不恶化超过 10%。这些为项目决策阈值，实验前登记，未达标则调整或不启用相应机制；不能预先宣称能达到。

没有专业球探标签时，仅报告 Agent 行为与证据保真，不把候选相同、token 降低或 Harness 通过称为推荐质量提升。

## 9. 用户看到的变化

用户修改要求后，案件立即显示新的有效条件；对过去已回答的问题减少重复追问。资料较多且确实进入分批步骤时，SSE 展示“正在分批比较候选”或“正在核对相关报告原文”，不显示 tokenizer、压缩比例、内部 schema 或模型隐藏推理。普通短请求应直接前进；长案件可以继续原调查，报告清楚表示实际比较范围。
