# TactiScout 全站 Beautiful UI 视觉升级

## Problem Statement

用户认为 Beautiful UI 的界面整体更有吸引力，希望 TactiScout 大面积吸收其组件与视觉语言，让等待、调查、阅读报告和评审过程都更清晰、舒服。当前产品已有可工作的招募、报告、盲评和裁决页面，但各页面尚未形成用户期望的统一、高辨识视觉体验；简单增加装饰组件也无法改善实际使用体验。

本规格承接已确认的激进视觉升级方向，覆盖所有面向用户的主要页面。它不把“组件数量”当作成功标准，而以视觉一致性、任务清晰度、证据可读性和交互反馈为目标。

## Solution

为主工作台、匿名短名单盲评、裁决和录制运行展示建立统一的深色高对比视觉体系，以 TactiScout 绿色作为识别色。重做共享导航与工作区外壳；桌面端提供计划导航、对话与进度、报告证据三个可调区域，小屏幕改用适合触控的紧凑导航和标签页。

在适合的场景广泛接入 Beautiful UI 的导航、输入、进度、推荐、证据、比较和记录展示组件，并适配现有 shadcn、Lucide、React 与 Tailwind 体系。通过明显但有用的反馈动效改善主要操作；盲评和裁决保留安静、专注的评分体验。报告默认突出结论、关键依据、数据缺口和不确定性，详细来源与样本可展开查看。

改版只调整界面表达和交互呈现，不增加招募、Agent、数据采集或评分能力。调查进度必须反映真实运行状态，不能展示隐藏推理、虚构的工具调用或假完成百分比。匿名评审、评分锁定、答案键揭示顺序、证据来源与缺失数据边界均保持不变。

## User Stories

1. 作为首次进入的球探，我想在所有面向用户的页面看到一致的导航和视觉规则，以便知道自己仍在同一款球探产品中。
2. 作为球探，我想看到深色、高对比且以 TactiScout 绿作为识别色的界面，以便界面整体具有清晰且鲜明的视觉个性。
3. 作为桌面用户，我想在同一工作区中查看计划导航、对话与调查进度、候选报告与证据，以便边调查边核对依据。
4. 作为桌面用户，我想收起或调整报告证据区域，以便按当前任务给对话或报告更多空间。
5. 作为手机用户，我想通过紧凑导航和标签页切换对话与报告，以便不必在窄屏上挤看多列内容。
6. 作为球探，我想使用清晰易触达的自然语言输入区和合适的提示入口，以便快速提出或补充招募需求。
7. 作为球探，我想在调查进行时看到明确的当前阶段、真实耗时与安全事件，以便知道调查还在做什么。
8. 作为球探，我想展开调查步骤查看已完成的真实阶段，以便回顾 Agent 实际执行过的工作。
9. 作为球探，在调查等待用户回答、执行中、取消、失败或恢复时，我想看到与真实状态一致的界面反馈，以便采取正确的下一步操作。
10. 作为球探，我想通过清晰的反馈识别发送、恢复、停止、保存和选择操作是否成功，以便避免重复操作或误解结果。
11. 作为球探，我想在推荐卡片中快速扫描候选身份、重点依据、主要取舍与样本限制，以便先判断是否值得深入查看。
12. 作为球探，我想按需展开完整指标、来源、赛事赛季、比赛样本与口径，以便在需要时核对推荐依据。
13. 作为球探，我想让证据缺口、小样本和未知项保持清晰可见，以便不把数据不足误认为能力不足。
14. 作为球探，我想按语义相近的卡片浏览案件摘要、能力覆盖和候选上下文，以便在大量信息中快速定位重点。
15. 作为球探，我想选择候选人后获得明确的比较或后续操作反馈，以便知道选择已生效且能继续处理。
16. 作为球探，我想在候选比较中并列查看相关指标和对应样本，以便比较不依赖记忆或来回切换页面。
17. 作为评审者，我想在盲评页面看到与主产品一致的视觉体系，同时保持匿名卡片和评审材料中不泄露球员身份，以便独立评分。
18. 作为评审者，我想在盲评页面降低无关动效和视觉干扰，以便专注阅读证据并提交判断。
19. 作为裁决者，我想在裁决流程中清楚识别当前阶段、锁定状态与可执行动作，以便遵循先独立评审、后揭示答案键的顺序。
20. 作为展示者，我想通过结构清晰的录制运行页面讲解真实发生的调查步骤，以便观众理解流程而不把静态摘要误认成实时运行。
21. 作为使用键盘的用户，我想通过明确的焦点样式和符合逻辑的顺序完成主要操作，以便无需依赖鼠标。
22. 作为使用辅助技术的用户，我想让状态、操作和数据表有清晰的语义名称，以便理解当前界面及其变化。
23. 作为偏好减少动态效果的用户，我想让动效尊重系统设置，以便仍能舒适使用产品。
24. 作为所有用户，我想让颜色、图标、文字和位置共同表达状态，以便状态识别不依赖单一颜色线索。
25. 作为所有用户，我想让表格和密集报告在窄屏中保持可读并避免整页横向溢出，以便可以在手机上核对关键内容。
26. 作为球探，我想在主工作台、盲评、裁决和运行展示中获得统一的排版、控件和反馈，以便不同工作流之间无需重新学习界面规则。
27. 作为维护者，我想把适用的 Beautiful UI 模式整合到现有 shadcn 组件体系中，以便复用组件行为而不引入另一套互相冲突的全局主题。
28. 作为维护者，我想只在能真实支持用户任务的地方使用 Beautiful UI 组件，以便产品不会为了展示组件库而增加不必要的信息或操作。

## Implementation Decisions

- 改版范围包括主招募工作台、`/review` 匿名短名单盲评、`/adjudicate` 裁决/质量评估和 `/showcase` 录制运行展示；开发专用位置选择实验页不属于用户产品改版范围。
- 采用统一的深色高对比基调，以现有 TactiScout 绿色作为品牌识别色。具体颜色、间距、字级、边框、阴影、焦点环和动效节奏由实现阶段建立为一组共享设计变量。
- 桌面工作区由计划导航、对话与进度、报告证据组成。报告证据区可收起或调整；小屏采用紧凑导航与对话/报告标签切换，避免把桌面多列缩小后直接塞进手机。
- 使用现有 shadcn registry 接入方式获取适用组件，并在项目内本地调整其样式和交互。沿用现有 React、Tailwind 与 Lucide 基础；逐个审核组件的额外依赖，只在价值明确时加入必要依赖。复制的上游代码保留 MIT 许可和版权信息。不要引入付费图标依赖。
- 组件映射：`SidebarNav` 的导航层级适配计划导航和全局工具菜单；`ChatComposer` / `PromptBar` 适配对话输入；`LoadingState` / `TaskRows` 适配调查中状态与进度摘要；`RecommendationCard`、`ContextCards`、`InsightCards` 适配候选、证据覆盖和上下文摘要；`DiffTable`、`RecordsTable`、`SelectionActions` 适配候选比较、来源记录与就近选择操作；`Flowchart` 可用于录制运行展示中的流程说明。所有映射必须复用现有数据和操作合同。
- 不要求逐个搬入 Beautiful UI 的全部组件。`ThinkingState`、`ToolChips` 和 `StreamingText` 不能暗示当前服务会输出隐藏推理、工具调用事件或逐 token 答案；`CodeBlock`、`FineTuneCard`、`GlideMenu`、普通 `ApprovalCard` 等无当前用户任务支撑的组件不纳入改版。
- 主要导航、输入、卡片展开、候选选择、比较操作和调查状态变化使用清楚且快速的动效反馈。动效表达真实交互，不制造背景活动、假进度或虚构工具结果；支持 `prefers-reduced-motion`。
- 盲评与裁决沿用统一深色视觉变量和组件语言，但减少装饰性运动与注意力竞争。匿名卡片结构、评分本地草稿、锁定动作、答案键访问时序和导出语义不变。
- 报告采用渐进披露：默认显示推荐结论、关键证据、取舍、小样本/缺失数据限制；完整来源表、指标定义和样本详情可展开查看。视觉简化不能隐藏会改变判断的数据限制。
- 不改变招募案件状态、Agent 工具或工作流、API/SSE 合同、数据采集、评分算法、匿名数据模型、浏览器持久化或服务端存储；本规格只改变现有能力的呈现与交互反馈。
- 旧有视觉研究 `.scratch/tactiscout-mvp/research/scouting-studio-redesign-2026-10-15.md` 中的浅色主题和保留双栏方向由本规格取代。其关于证据覆盖、未知项、窄屏和现有业务能力的约束仍适用，研究文件本身保持不变。

## Testing Decisions

- 好的自动化测试验证用户能看到什么、能执行什么，以及隐私和数据边界是否保留；不检查 Tailwind 类名、CSS 实现方式、内部组件结构或上游组件源代码细节。
- 沿用现有页面和工作台组件作为最高可复用的自动化验收面：主工作台覆盖新建、调查中、等待回答、恢复/停止和报告状态；报告覆盖依据展开与比较操作；盲评覆盖匿名显示和评分状态；裁决覆盖锁定阶段；运行展示覆盖静态摘要语义。
- 优先扩展已有行为测试：`web/tests/recruitment-conversation.test.tsx`、`web/tests/active-session.test.tsx`、`tests/web/web-progress.test.ts`、`tests/web/report-presentation-ablation.test.ts` 和 `tests/web/shortlist-review-workspace.test.ts`。只有现有 seam 无法验证用户行为时才增加最高层级的新测试 seam。
- 实现后运行 Web TypeScript/Vite 构建检查；自动化验证不以真实模型或网络数据为条件。
- 通过实际浏览器逐页检查桌面和窄屏下的共享导航、三区域工作台、输入、实时/等待/终止状态、报告证据、盲评与裁决、录制运行展示；检查键盘焦点、减少动态效果设置、可读对比、窄屏溢出和表格自身滚动。视觉层级和动效质量不使用 CSS 类名断言替代。
- 不新建 Playwright 或其他浏览器自动化基础设施；浏览器检查采用现有可用的手工验收方式。

## Out of Scope

- 新增 Agent 思维链、工具调用名称或模型 token 流的展示能力。
- 新增进度百分比、预计完成时间、虚构活动动画或新的调查状态。
- 新增候选筛选、批量操作、收藏、评分算法、球员数据或报告字段。
- 改变盲评身份隔离、评分、锁定、裁决或答案键的数据与业务流程。
- 为逐个使用组件库组件而新增当前产品没有的审批、代码展示、模型微调、搜索或悬浮菜单功能。
- 引入新的服务端 API、SSE 事件、Agent 状态管理或持久化设置。
- 新增浅色/深色主题切换偏好；本规格采用已确认的深色方向。

## Further Notes

- 参考组件库：`https://github.com/slev12397/beautiful-ui`。实现时应再次核对 registry 组件当前依赖、许可和源文件内容，不要以组件名称相似代替语义适配。
- 领域术语遵循根目录 `CONTEXT.md`，尤其是“调查进度”“招募案件”“分析快照”“盲评提交”和“人工裁决等级”的边界。
- 实现顺序：先建立共享主题和导航/工作区外壳，再改主工作台交互与进度、报告与比较，然后统一盲评/裁决和录制运行展示，最后完成全路由浏览器验收。
