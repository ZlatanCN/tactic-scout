# Planner 延迟审查与实验纠正（2026-10-18）

## 已确认的测量

巴萨后卫需求的两次真实整图运行分别耗时 91,123 ms、78,586 ms；其中唯一一次 expand 模式 Planner 调用分别耗时 60,541 ms、53,374 ms。工具耗时分别约 8,106 ms、2,602 ms。说明这两次运行主要等待模型，但不能推断其他运行或所有阶段的唯一根因。

本机 OpenAI 兼容请求中，reasoning_effort=none 的简单算术返回 content=2；未设置时返回 reasoning 且耗尽 64 token。该结果支持本机接口识别此参数，不能单凭简单算术证明全部整图调用都没有额外推理成本。

## 未成立的因果结论

此前“系统提示词是决定性根因”“schema 枚举是决定性根因”“预填充成本超线性”均证据不足。实验没有充分控制输出长度、预热、前缀缓存、执行顺序及模型负载。一次 expand 调用慢，也不能归因于只在 investigate/reorient 中使用的常驻指令。

把 Modelfile 中 temperature=1 直接解释为覆盖请求中的 temperature=0 也没有请求级证据，不应作为事实。

20/3/1 候选探针没有同步改变全部 history 和覆盖计数，因此不能用于候选数量的有效消融。缺少 token 分阶段耗时的总耗时不能称为“纯预填充耗时”。

## 失败实验及处理

将枚举改成字符串、superRefine、transform 均没有得到可信性能收益。实验中的真实整图耗时 368,590 ms，经历 expand 超时后扩页，最后 conclude 花费 194,238 ms；路径已改变，不能与原先单次 expand→finish 直接比较。移除枚举还使模型产生未授权候选，transform 静默过滤会掩盖错误。全部此类生产改动已撤回，保留原有候选、证据键和报告 ID 白名单。

只移除 reportObservations 不可用分支中 linkedMetricKeys 的全量枚举：该数组 max=0，任何非空数组仍被拒绝；不声称此处精简已经提升实测速度。

## 已完成的可靠性修复

- 能力画像 basis=ability_profile 的无比赛百分位状态合法；Harness 不再误判，错误原因仍拒绝。
- conclude/reorient 超时保留已经取得的证据，通过原 Reviewer 安全生成有限报告。
- trace 延迟归因先验证 decisionMode 是字符串，后端恢复可构建。
- HTTP 服务根据最终响应补齐 completed/waiting_for_user/cancelled 状态；SSE 断线不取消服务端案件。
- HTTP 回归按实际 progress/result 事件封装断言，并验证完成事件先于最终结果。

## 下一步实验要求

冻结真实 Planner 输入、来源快照和模型配置。对同一输入按交错顺序运行基线与候选优化，记录系统/context/schema 字符数、输入输出 token、调用模式、动作、合法引用、失败与回退、总耗时。先验证单调用，再用整图检查路径和报告质量。候选/证据不得为缩短输入而截断或静默丢弃。至少三对，仅有微基准收益不直接上线。

usedMultipleModelActions 只反映模型动作数量，不能代表推荐质量，也不能要求产品为了通过指标而增加模型调用。保留原计数供诊断，后续应区分场景专属的编排要求与通用正确性要求。

## 巴萨后卫长尾的配对验证

见 [issue 217](../issues/217-shorten-evidenced-barcelona-defender-expansion.md)。在同一完整 LangGraph、同一冻结 Understat 数据、同一本机 `tactiscout-qwen3.5:9b` 和同一请求下，交错运行三对“能力充分时确定性收束”与“仍交给扩页 Planner”的实验。两臂 3/3 均通过 Harness；收束臂没有扩页 Planner 请求，端到端 p50 / p95 为 56.513 / 61.378 秒；对照臂每轮都发起一次扩页 Planner 请求并在等待后回退，p50 / p95 为 114.473 / 122.162 秒。两臂均输出 3 名推荐、5 条证据引用，能力覆盖计数一致；三对的推荐身份顺序和证据顺序均相同。

这支持移除“已有足够证据后仍咨询扩页 Planner”的无收益等待，并保留“证据不足时继续由 Planner 决策”的路径。它仍不证明推荐排序更好，也不证明高位防守战术适配已被数据核验；当前映射仍是能力画像职责代理。

## 已完成的来源指令消融

见[固定输入方案与结果](../../planner-context-serialization/spec.md)。生产Planner中来源专属指令按dataMode注入，三对固定两人任务输入4868→3776token；耗时中位数74915→41375ms，但一对变慢、两对变快，输出长度也改变。精简组3/3通过候选/指标/报告引用核验，基线三次都有不存在的报告引用。只验证本案例的指令成本与引用行为；不能推广为完整引援质量或conclude阶段提速。当前后端633/633、前端SSE8/8及API/Web构建通过，完整巴萨对话长尾仍待优化。
