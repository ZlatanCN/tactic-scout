# 前端重构：对抗性审查与消融协议

日期：2026-10-15

范围：当前 Tailwind + shadcn + Beautiful UI 提案，以及主工作台的状态组织和报告呈现。此次是方案与源代码审查，没有执行新的浏览器用户实验，也不构成全站视觉或无障碍审计。本文不改产品代码。

## 第一性原理

用户要决定下一步考察谁、为什么、尚缺什么依据，以及怎样继续调查。运行中要能理解当前进展、回答必要问题、停止或恢复调查。

有来源记录、有目标能力证据、值得进一步考察、适合引援是不同判断；前端不能把它们互相替代。保存的报告与本轮正在执行的需求必须能区分。网络断开也不等于服务端调查已停止。

组件库负责降低实现和维护成本。它的存在不能作为上述任务已经改善的证据。文件行数同样不足以证明重构收益。

## 审查结论

### HIGH：名单整体状态掩盖逐人证据差异

证据：`web/src/RecruitmentReportPanel.tsx:91` 的 `hasFocusEvidence` 使用 recommendations.some；`backgroundOnly` 随之成为报告级布尔值。随后每张 RecommendationCard 都收到相同的 backgroundOnly 和 comparisonAvailable。

反例：A 有重点指标，B 只有同位置背景记录。只要 A 存在，B 也进入带排名、比较入口的同一展示分支。该结论来自源代码控制流；本次没有把它描述为已在浏览器复现。

处理：分别推导候选人的证据状态，再聚合报告摘要。比较可保留未知项，但未知应明确显示，不能因为 A 有依据就把 B 包装成已经完成同等评估的推荐。

### MEDIUM：空名单的恢复建议推断过度

证据：`web/src/RecruitmentReportPanel.tsx:131` 对所有空名单统一解释为没有符合检索条件的记录，并建议放宽位置、年龄或赛事。recommendations.length === 0 不能单独证明这个原因。

处理：已有契约若能区分检索无结果、评估缺证据和来源不可用，则逐项使用；契约不能区分时保留原因未知的表达。不能自动暗示用户应改变原本合理的引援需求。

### MEDIUM：视图掌握了调查运行的整套生命周期

证据：`web/src/App.tsx:103` 起管理会话、报告、计划、loading、待确认请求、取消和连接状态；轮询在同一文件的 effect 中；提交、恢复和计划存储也在该文件。`web/src/turn-requests.ts`、`web/src/api.ts`、`web/src/plans.ts` 已提供可以复用的实现。

处理：把提交、追问后继续、取消、断线恢复收拢到一个调查会话模块。对页面暴露当前状态和 submit/resume/cancel 等必要动作。保留 requestId 的重试语义和旧报告快照。内部用 TypeScript 明确状态转换；暂不增加全局状态库或第二套状态机。

### MEDIUM：引入两套设计基础会延续样式叠加

证据：当前 `web/src/styles.css` 和 `web/src/workbench.css` 已同时提供全局与工作台样式；Beautiful UI README 另有 foundation、全局 token、动画和额外依赖。TaskRows 源码还包含演示用计时序列，仓库 harness 使用脚本场景。

处理：只建立一套 TactiScout 语义 token。Tailwind v4 与 shadcn 提供基础；Beautiful UI 逐项审查后取用，适配到同一套 token。调查状态必须由真实服务事件驱动。不要把演示倒计时、百分比或自动失败转成功序列带入产品。

## 最小方案

保留 React + Vite。选择 Tailwind v4 和一种 shadcn primitive 基座；当前建议 Base UI，但项目没有需要同时引入 Base UI、Radix 和 React Aria 的已证实需求。

对 Agent 呈现优先评估 shadcn 自带的聊天、追问和步骤模式。Beautiful UI 作为按需取用的代码和视觉参考，不作为第二套全局系统。来源归属、许可和实际依赖随复用的文件保留。

首批只有三个业务模块：

- 调查会话：管理提交、等待追问、运行、取消、恢复及报告快照，内部使用现有 API 和计划存储。
- 对话工作区：呈现输入、必要的追问、真实运行进展；消费会话模块，不管理网络生命周期。
- 球探报告：逐人推导证据呈现，再组合结论、名单、比较和来源。只负责展示，不另算球员能力评分。

基础控件放 `components/ui`；相关业务代码放 `features/recruitment`。先迁移一个完整调查流程，迁移后删除相应旧样式。避免为单次调用建立 pass-through wrapper，避免预先增加插件系统、通用 Renderer、事件总线、全局状态库和额外 UI 框架。

## 必须验证的机制

工程验证与用户体验验证分别记录。自动检查能够证明状态和证据没有被错误呈现；它不能证明用户更快理解或更信任产品。

采用冻结的报告快照和真实事件录制，在本地重放。同一实验两臂使用相同数据、文字事实、信息量、事件时间和操作能力；只改变目标机制。无需重复调用模型，也不拿不同模型结果比较布局。

| 消融 | 完整臂 | 去除臂 | 任务与记录 |
| --- | --- | --- | --- |
| 结论优先 | 首屏展示判断、关键依据和主要缺口 | 同样内容保留在名单后的摘要中 | 判断哪些人有目标能力证据、哪些人仅有背景记录；记录正确率、误判和完成时间 |
| 渐进披露 | 关键结论与缺口常显，完整指标与来源详情展开 | 同样内容全部展开 | 查出赛季、分钟、一个缺失指标和来源；记录正确率、时间、展开和往返操作 |
| 有意义的实时进度 | 展示实际事件的用户可读步骤、计时和停止 | 通用运行提示、相同计时和停止 | 区分运行、等待补充、连接中断和停止确认；记录误判、重复提交和放弃。真实重放时长必须相同 |

最少覆盖六类输入：目标证据充分、部分能力缺失、全部目标能力缺失、不同证据状态混合名单、空名单、追问后继续。运行状态补充取消和连接中断重放。未知不显示为零，旧报告不冒充新结果；这些是两臂都必须满足的正确性约束。

先做可重复的浏览器任务检查和行为断言，由实现方完成，定位功能和文案错误。有人参与时，用不同但相当的案例平衡版本顺序，避免同一答案重复出现带来的学习效应；记录参与人数、案例和原始结果。少量或仅实现方参与的结果只作为探索证据，不宣称统计显著，也不要求用户提供专业评委作为开发前置条件。

预先确定判定方向：第一项优先降低证据误读；第二项在不降低核查正确率的前提下减少操作和时间；第三项降低状态误读和重复提交。结果不支持机制时，删除或调整该机制。不能用截图偏好、人工智能自评分或构建成功替代任务结果。

组件库选型使用另一份工程记录：相同垂直流程所需的新增直接依赖、重复控件数量、独立 token 数、需要维护的适配代码以及键盘行为。它不是上述用户体验消融的一条实验臂。

## 当前证据状态与实施顺序

- 已完成：读取主工作台、报告、进度归并、请求恢复和 API 契约代码；识别上述控制流和提案风险。
- 未完成：新栈接入、六类快照的完整重放、各消融臂实现、参与者任务实验。因此目前没有重构提升效率或降低放弃率的实验结论。
- 顺序：修正逐人证据语义和空结果表达 → 收拢会话生命周期 → 接入一套设计基础并迁移主工作台 → 执行重放与消融 → 根据结果收敛界面 → 再迁移比较和辅助页面。
