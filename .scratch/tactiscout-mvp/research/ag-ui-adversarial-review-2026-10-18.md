# AG-UI 前端接入：第一性原理与对抗性审查

**日期：** 2026-10-18  
**范围：** 审查当前“为 TactiScout 接入 AG-UI/TanStack AI”的提案。本文只定义产品假设、验证边界与决策门槛，不修改应用代码。

## 结论

当前提案应缩成一条可删除的 SSE 实验，暂不全面接入 AG-UI，也不让 TanStack `useChat` 接管现有会话。

用户真正需要的是：**长任务期间及时、可信地知道系统正在做什么，并能停止、恢复或回答追问。** 当前实现已经产出安全的 LangGraph 阶段事件，并有请求级幂等、同案排队、取消和恢复。AG-UI 最多改善这些事件到达浏览器的传输方式；它不会提升候选发现、身份解析、证据质量或推荐理由。

因此，首个实验只回答一个问题：

> 在不改变同一 LangGraph、数据、Planner、报告和业务状态的前提下，SSE 相对现有 1.2 秒快照轮询，能否显著降低阶段更新延迟与请求量，同时保持取消、恢复、追问和报告完全一致？

实验通过后，才决定是否需要 AG-UI 标准化。若普通 SSE 已经解决问题，AG-UI 是后续互操作选项，不应先引入。

## 第一性原理

从用户任务拆开，前端链路只承担四件事：

1. **发出一次有身份的业务命令。** 案件、请求和结构化答案不能因协议更换而失去校验。
2. **在任务执行期间看见真实进展。** 只展示 LangGraph 已发生的阶段，不用动画或模型自述伪造进度。
3. **在暂停、取消或断线时得到明确状态。** “连接结束”不能自动解释成任务完成、停止或失败。
4. **拿回可保存、可复核的结构化结果。** 报告是领域对象，不能降格成聊天文本。

AG-UI 的通用能力主要在第 2 项和第 3 项的传输层。第 1、3、4 项的业务语义仍由 TactiScout 持有。把协议层收益当成完整产品收益，会高估接入价值。

## 现状基线

- LangGraph 节点通过 `emitProgress` 发出白名单阶段事件；回合运行时将其投影为 `onProgress`。
- Fastify 当前等待整个回合完成后返回 JSON，同时把阶段快照写入案件内存表。
- React 每 1.2 秒读取一次 `/progress` 快照，并使用请求 ID 避免显示同案上一轮状态。
- 前端以 `caseId` 保存 checkpoint 身份、以 `requestId` 处理去重、排队、取消和结果恢复；当前回合消息、报告和计划另由 `useRecruitmentSession` 持有。
- 现有 `cancelled` 是服务端图实际退出后的终态；“正在停止”仍是进行中。断线恢复通过重发原请求取回相同结果，不重新运行图。

这说明真正要替换的代码很少：主要是快照轮询到事件订阅这一段。业务执行、报告和会话状态不需要随之改写。

## 提案的对抗性审查

| 风险 | 失败方式 | 必须保留的约束 |
|---|---|---|
| 用户问题不成立 | 阶段已可读，换成流式后用户几乎没有感知改善 | 先用同一冻结图测更新延迟；若多数阶段延迟已远低于用户可感知阈值，停止接入 |
| 协议替换掩盖业务缺陷 | SSE 看起来更“Agent”，但空名单、错误身份和弱证据完全没变 | 报告与追问 schema 逐字段等价；不把传输实验算作球探质量提升 |
| 一次改多个变量 | SSE、AG-UI、TanStack client 同时变化，无法判断收益来自哪里 | 分阶段消融：轮询 / 原生 SSE / AG-UI 线格式；客户端仍先保留现有会话层 |
| 两套状态互相覆盖 | `useChat` 和 `useRecruitmentSession` 同时维护消息、加载和错误 | 领域会话只有一个所有者；流只更新调查时间线 |
| 连接中断被误当取消 | 浏览器关闭流，服务端图仍执行；或界面误报失败 | 显式停止继续走服务端 cancel；断线恢复按原 `requestId` 取结果 |
| SSE 自动恢复的错觉 | 重连后丢事件或重复事件，旧阶段重新出现 | 事件必须有单调序列；重连先补快照或按游标续传，并去重 |
| 流放大泄露面 | 转发原始 LangGraph state、工具参数、提示词或异常正文 | 只发送现有白名单字段；用 canary 验证内部状态不进入任何事件 |
| 长连接生命周期错误 | 客户端提前结束、服务端继续写，或响应永不关闭 | 真实 HTTP 测试流的启动、终态、异常和连接关闭 |
| 移动端与代理限制 | 缓冲、断线、休眠后恢复表现不同 | 真实浏览器和 Vite 代理验证；不能只测 Fastify `inject()` |
| 维护成本超过收益 | 新增协议适配器、状态映射和升级门槛，却只省一个轮询 hook | 记录新增/删除的生产代码与依赖；没有明确第二客户端就保留普通 SSE |
| 框架能力被误读 | 把 AG-UI 的 LangGraph 适配器当作可直接接管当前本地运行时 | 适配器、部署模型、interrupt 语义必须先通过最小真实链路验证 |

## 奥卡姆剃刀下的分层

### A. 原生 SSE 纵向切片（先做）

Fastify 增加实验端点，仍调用同一个 `recruitmentConversation.turn()`。服务端在现有 `onProgress` 回调中发送按序事件，终态发送完整且经 Zod 校验的现有 `ConversationTurnResponse`。前端复用 `useRecruitmentSession`，只把进度来源换成事件订阅；轮询端点保留作回退。

新增的稳定接口只需：

```text
POST /api/v1/recruitment/cases/:caseId/turns/stream
```

请求体沿用现有 turn schema。首个事件标识请求，后续只含已脱敏的 `RecruitmentProgressEvent`，最后一个事件携带现有完整响应。取消继续使用现有 cancel 端点，避免第二条停止语义。

这一步不引入 AG-UI，不新增消息状态，也不改 LangGraph。

### B. AG-UI 线格式（仅在 A 通过且互操作有需求时）

保留同一条 SSE 执行路径，只把事件映射为 AG-UI 生命周期、自定义进度和最终结果事件。`caseId` 映射 `threadId`，`requestId` 继续是业务幂等与取消身份。AG-UI 的 `runId` 不能替代它。

这一层应证明：

- 外部 AG-UI 客户端能恢复当前结构化问题并继续同一案件；
- 不需要复制或放宽现有业务 schema；
- 取消、恢复与报告在两条路径逐字段一致；
- 新增适配器确实可被第二个消费者复用，而非只服务同一页面。

### C. TanStack `useChat` 接管（默认不做）

只有出现独立聊天产品需求，并且能删除现有会话状态代码时才评估。若它只替换 SSE 解码却迫使项目保留两套消息与恢复状态，就不采用。

## 消融设计

### 实验单位与固定项

每次实验是一条完整招募回合，包括追问、回答、取消或恢复。所有实验臂固定：

- Git 提交、数据快照哈希、赛事/赛季与仓库实现；
- Planner、模型、知识库、工具预算、图节点和边；
- 案件与请求脚本、答案、取消时点；
- 浏览器与运行机器、API 监听方式、冷/热缓存状态。

每臂至少重复 5 次；样本很小时只报告原始观测，不宣称稳定性。

### 臂 1：现有快照轮询

保留 1.2 秒轮询，作为行为与资源基线。

### 臂 2：原生 SSE

只把进度传输改为 SSE，其他完全不变。

### 臂 3：SSE 无实时进度

SSE 只在终态返回结果，不发送中间事件。这是**负对照**：它验证收益确实来自事件到达，而不是“请求换了 URL”或测试偶然性。

### 可选臂 4：AG-UI 线格式

仅在臂 2 通过产品门槛后运行，并保持同一事件内容与终态业务对象。用于判断协议标准化是否有独立价值，不与球探效果混在一起。

不需要立即做“轮询间隔 500 毫秒 vs SSE”的臂。它可能缩短延迟，却会增加请求量，属于同一体验曲线的另一端点，等主假设成立后再调优。

## 可验证指标

| 指标 | 定义 | 用途 |
|---|---|---|
| 阶段可见间隔 | 实验端点记录服务端发布时刻并随事件发送；浏览器用 `PerformanceObserver` 记录收到与绘制时刻。分别报告服务端间隔、流内传输间隔和客户端可观察间隔，不把三者合成无法直接测量的“端到端延迟” | 核心体验收益 |
| 用户可感知改善 | 每轮事件延迟相对 1.2 秒基线的减少量，以及首个阶段、首次追问前的等待变化 | 防止只优化不相关尾部事件 |
| 请求数与字节量 | 每次回合的 HTTP 请求数、响应/事件字节数 | 判断长连接是否真正减负 |
| 连接建立成本 | 首事件时间、流建立失败率 | 发现代理或移动网络问题 |
| 业务等价 | 状态、问题 schema、报告 JSON、限制与来源引用逐字段一致 | 防止流式改造破坏产品结果 |
| 事件一致性 | 序列单调、无重复、无丢失；界面时间线与 Harness 工具轨迹对应 | 防止虚假或错序进度 |
| 恢复与幂等 | 重复请求不重跑；断线后取回同一结果；不把断线当取消 | 保留当前可靠性 |
| 取消闭环 | 服务端图收到 signal、实际退出、记录取消终态、同案下一回合可继续 | 防止只关浏览器连接 |
| 安全 | canary 提示词、工具参数、原始 state 和异常正文均不出现在流中 | 防止扩大泄露面 |
| 维护成本 | 生产代码、测试和依赖的净增行数与新增状态源数量 | 防止协议债务 |

轮询臂无法读取服务端阶段发布时刻，因此对照应使用每个阶段的“相对回合开始的可观察到达/绘制时刻”，再与 SSE 的服务端发布、传输和绘制三个分段一起解释。延迟应同时报告原始毫秒和相对改善，不只用百分比。事件过密时还要记录浏览器主线程长任务，防止流式更新反而卡顿。

## 场景矩阵

| 场景 | 必须观察 |
|---|---|
| 正常完成 | 阶段时序、终态、报告逐字段一致 |
| 追问并同案回答 | 问题控件、结构化答案、恢复后的阶段正确 |
| 主动停止 | 停止请求中状态、实际取消终态、同案队列释放 |
| 浏览器断线再恢复 | 服务端继续或完成时，客户端按原请求取回，不产生第二轮 |
| 流建立失败 | 明确回退到轮询，不把失败解释成任务失败 |
| 终态前连接关闭 | 图实际终态仍可恢复，不重复执行工具 |
| 同案连续提交 | 排队、幂等冲突与取消后下一回合语义不变 |
| 小样本/空名单报告 | 报告与追问内容不受传输方式影响 |

## 决策门槛

全部条件满足才继续：

- 至少一个代表性冻结场景中，阶段更新 p95 延迟相对轮询有明确且可重复的改善；
- 用户最常看到的首个阶段、工具阶段和追问前提示确实受益，而非只有末尾事件；
- 正常连接请求量下降，字节量没有明显膨胀；
- 报告、追问、恢复、幂等和取消全部等价；
- 浏览器长任务和移动网络没有实质退化；
- 生产代码与状态所有权保持简单，实验端点可以单独删除。

出现以下任一情况就停止：

- 延迟改善低于用户可感知阈值，或只有少数尾部阶段受益；
- 必须复制现有会话状态才能接入 TanStack client；
- 流恢复需要另建一套与 `requestId` 竞争的运行身份；
- 为兼容协议而削弱 Zod 校验、隐藏未决状态或把报告文本化；
- 维护成本大于删掉的轮询和传输代码。

## 建议的后续 issue 切片

1. **SSE 传输实验：** 单一实验端点、事件序列、终态响应与安全白名单；用真实 HTTP 测试完整链路。
2. **配对体验测量：** 轮询、SSE、无进度 SSE 三臂，报告延迟、请求量、业务等价和浏览器性能。
3. **产品决策：** 达到门槛才保留 SSE；否则删除实验端点。
4. **AG-UI 互操作实验：** 仅在已有第二个客户端需求时，将已通过的 SSE 映射为 AG-UI；继续以现有 turn schema 为业务真源。

## 当前决策

**先做原生 SSE 实验，不全面接入 AG-UI，不让 TanStack `useChat` 接管会话。** 这是当前证据下最少新增概念、最容易回退、也最能直接检验用户价值的方案。
