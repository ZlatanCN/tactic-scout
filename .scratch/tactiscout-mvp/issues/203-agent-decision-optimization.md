# 203 — 优化球探调查决策机制

Type: task
Status: resolved
Labels: ready-for-agent

## Objective

从引援调查的用户可见目标出发，验证参考球员画像、候选比较、确定性调查步骤、Reviewer 恢复和按需 RAG 是否真正改变调查行为或报告。保留必要机制，去除没有决策证据的隐藏上下文；不以 Harness 行为或单个案例声称球探推荐准确率提升。

## Acceptance

- [x] 替代者调查读取目标队现有球员数据，参考球员不进入推荐；只展示来源、赛事、赛季和指标均可比的实际观测。
- [x] 候选比较依据可追溯，并与职责适配判断分开；报告开关可独立关闭。
- [x] 对确定性必需步骤做同图配对对照，核对有效搜索、候选、Planner 次数、token 与耗时。
- [x] 验证 Reviewer 能对具体错误发起受约束恢复，并对照 Reviewer 关闭后的报告与成本。
- [x] 对照固定检索和按证据缺口检索，区分节省空检索与真正的 RAG 质量收益。
- [x] 以全量回归和 API/Web 构建复核实现。

## Implementation

- 参考画像由 `inspect_team` 写入 LangGraph typed state；只作为报告可见的来源数据，不放入 Planner 对话或提示词。推荐规则显式排除参考球员。参考指标缺失时不补零。
- 候选比较只对相同 provider、位置、赛事、赛季和指标口径的记录展示观测范围；与参考球员的比较单独展示。两种说明都不生成综合分或声称适配优劣。
- `choose_next_action` 先执行确定的必需调查，再在需要判断、扩样或追问时调用 Planner；扩页继续遵循数据源返回的游标。
- Reviewer 针对错误的证据键和候选恢复，修复失败时只移除无效推荐/附录，保留通过逐人核验的候选。
- RAG 根据职责说明和能力证据缺口决定是否搜索。正式配置采用按需检索、确定性必需步骤和开启 Reviewer。
- 删除不再被调用的 `referenceProfilesFromHistory` 历史解析 helper，避免恢复已取消的“把画像塞回对话历史”路径。

## Frozen-model ablation

使用本机 Qwen 3.5 9B、相同自然语言请求与答复、相同 Understat 冻结快照 SHA-256 `9398c6515cd10d8b96d23bf4120e6bad2751375b7e5eca3bfddedbee0e5d50e2`。每个方案按正序/逆序各运行一次，共 12 次；12 次均完成了候选搜索和候选评估。真实运行结果位于 Git 忽略目录 `.data/evaluations/agent-optimization/results-v3-final.json`。成本以每臂两次实际调用汇总；耗时波动较大，因此不从两次运行推断一般延迟收益。

| 方案 | Planner 调用 | Token | 耗时（两次） | 可观察结果 |
| --- | ---: | ---: | ---: | --- |
| 基线 | 4/次 | 10,362/次 | 133.4s、94.3s | 两次均 5 个唯一候选；同一名单 |
| 参考画像展示关闭 | 4/次 | 10,362/次 | 84.3s、95.2s | 两次均与基线为同一名单；只少了参考画像/参考对照展示 |
| 候选比较说明关闭 | 4/次 | 10,362/次 | 92.3s、96.5s | 两次均与基线为同一名单；只少了候选间比较说明 |
| 绕过确定性必需步骤 | 7/次 | 16,633/次 | 159.8s、122.1s | 两次仍完成有效调查并给出与基线相同的 5 人名单；但多出 3 次 Planner 调用、token 增加 60.5% |
| 按需 RAG | 3/次 | 7,962/次 | 98.2s、71.5s | 两次均跳过无缺口的资料检索，评估覆盖仍包括 28 名候选；名单为 4 个不同候选，与基线不同 |
| Reviewer 关闭 | 3/次 | 7,767/次 | 52.7s、54.2s | 两次都输出两条同一球员的重复推荐（仅 1 个唯一候选）；Reviewer 开启时，基线两次都先拒绝一次问题报告，再通过恢复得到 5 个唯一候选 |

## Findings

1. **保留确定性必需步骤。** 两次旁路仍得到与基线相同的候选名单，但需要 7 次而非 4 次 Planner 调用，token 增加约 60.5%。这是本轮最清晰的成本证据；没有证据表明多出的模型规划带来更多可观察价值。
2. **保留 Reviewer。** 关闭 Reviewer 少一次 Planner 调用、少约四分之一 token，但两次都产生重复球员。基线的 Reviewer 恢复拒绝了无效报告，并在第二次复核中通过；这里验证的是名单去重/证据行为，不是排序质量。
3. **参考画像和候选比较是报告证据，不是已验证的排序机制。** 同一需求下开关只改变可见的说明，不改变 Planner 调用或候选名单。代码与整图回归确认 Planner 不接收隐藏画像/比较字段。继续展示它们的理由是让用户核对参考数据和同范围观察，不宣称提升推荐质量。
4. **保留按需 RAG 默认策略，但不声称已验证 RAG 质量。** 固定检索在本场景搜索了方法和球员报告，均未取回片段；按需模式跳过这些空搜索，少一次 Planner 调用并减少 token。它同时给出不同的 4 人名单，因此现有对照不能判断哪份名单更好；需要人工标注的候选质量集，才能作质量结论。
5. **LangGraph 的实际价值仍是显式案件状态、条件路由、可持久化暂停/恢复和 Reviewer 回环。** 本轮没有理由再增加 Agent、子图或更多节点。候选图级优化是：如果 PlayerElo 与历史档案两个独立补充源都实际启用，且延迟分析显示它们占时，再测 Reviewer 后并行 enrichment/join。本次实验中历史档案被权限门禁关闭、PlayerElo 未执行，因此并行化收益尚未测量，暂不改图。

## Answer

本轮按目标完成机制简化和有界消融：确定性步骤与 Reviewer 有可观察的保留理由；参考球员和候选比较保留为透明报告资料；按需 RAG 只证明可以跳过无结果检索。LangGraph 不需要为了“体现价值”再叠加 Agent 或子图。若以后要做图级性能优化，先评估两个独立 enrichment 是否同时启用，再测并行汇合是否缩短真实用户等待，同时要求报告与证据不变。
