# Agent Harness 行为评估套件

Type: task
Status: resolved
Labels: ready-for-human

## Goal

为 TactiScout 的自然语言球探案件建立可重复的行为评估：固定代表性场景，检查模型驱动的工具编排、追问恢复、证据边界和已知数据限制，并能通过重复运行暴露随机性。

## First-principles boundary

- 本轮只评可由数据集、接口契约或明确项目规则判定的行为不变量；不把单次成功或 LLM judge 输出说成球探质量证明。
- 演示球员集没有正确排序标签，因此不测 NDCG、Top-k 命中率或推荐准确率，不引入臆造的综合分。
- 当前方法语料仍很小：两篇 CC BY 论文（一篇项目作者摘要、一篇 PLOS 全文来源），具名球员报告语料为空；可以检查方法检索是否被调用，但没有足够标注计算 RAG 相关性/召回率。
- 代表性场景至少覆盖：有明确位置的巴萨年轻中场需求；凯恩接班人需求需先查证、在关键角色歧义处追问、补答后同案续查；演示数据缺少中锋时不得跨位置凑推荐。
- Trace 可记录动作名、真实结构化筛选范围（不含自由文本姓名/查询）、调用结果数量、耗时和候选 ID；不得输出隐藏推理、原始对话或模型凭据。

## Public seam

继续使用 `pnpm eval:local-agent` 作为本机真实模型的外部验收入口。默认行为与现有单场景用法兼容；新增具名场景、全场景运行及有限次数的重复运行。场景契约和纯评估逻辑由 runner 与确定性测试共用。

## Acceptance criteria

- [x] 评估数据集以稳定 ID 描述用户输入、可选补答和每场景的硬性期望；场景描述不把具体的推荐球员或排序当作真值。
- [x] CLI 可单独运行标准场景、接班人追问场景或全量数据集；可设置 1–10 次重复运行，每次使用独立案件 ID。
- [x] 每次运行给出通过/失败检查及不含隐藏推理、原始查询和球员姓名的工具轨迹；总体摘要给出通过比例、失败检查及 p50/p95 耗时。
- [x] 每场景评估是否遵守目标球队/筛选边界、必要工具与评估阶段、调查后追问、同一 thread 恢复、已声明的位置约束、证据支持，以及空数据时诚实等待或报告限制。
- [x] 对推荐排序准确性明确输出“不评估：缺少可信标签”，不能将空索引/空候选误记为相关性失败或能力低分。
- [x] 可用独立已知 trace 证明所有关键条件一旦违反就失败；测试通过 evaluator 的稳定调用接口，不访问真实模型服务。
- [x] Ollama 配置可用时，运行全量场景一次并记录实际耗时与各硬性检查；不得把单次通过描述成可靠性/统计显著性结论。
- [x] 真实模型 Harness 将 LangGraph 的安全进度事件与实际工具 trace 对照，检查每个工具调用都有对应阶段生命周期，并检查等待用户/完成终态与对话状态一致。
- [x] 进度轨迹必须与工具调用一一对应；多余、缺失、阶段不符、成功/失败终态不符或跨轮次配对均判失败。
- [x] 凯恩接班人场景覆盖两次按需确认；中锋位置无样本后，只有用户同意扩围才可搜索更宽的前锋位置，并按新的位置范围评估与报告。

## Adversarial review questions

- evaluator 是否只是把当前 prompt 和同一模型输出复述成“期望”，导致自我验证的循环论证？
- 某场景若没有可用球员、没有球员报告或正确结果是继续追问，检查能否区分“诚实停下”和“任务失败”？
- 重复运行是否真正创建独立案件，是否会错误地把先前 checkpoint 或上一轮 trace 带入？
- 汇总通过率是否会掩盖某一条关键安全不变量在一次运行中的失败？
- 隐私检查是否覆盖 stderr trace 和 JSON 结果的每一条输出路径，而不是只检查成功摘要？

## Answer

## Comments

### 2026-10-12 — 审查修正推进证据边界

对固定基准以来的规格审查发现：泛称“推进”曾把普通带球与长传次数列为直接指标；明确要求“带球推进”时，也会把渐进传球当作替代证据。现将泛推进映射收窄为渐进传球、其成功率和完成的穿线传球；带球推进当前保持不可测。确定性 Reviewer 现在会拒绝没有任何用户所求能力直接指标支持的推荐，重试仍失败时输出空名单。通过 `createRecruitmentConversation` 整图回归覆盖普通带球/长传拒荐、传球指标不得替代带球推进，以及支持渐进传球需求时继续分页。Harness 场景和模拟基准已同步；本次不评估真实球员排序质量。

### 2026-10-04 — 空位置结果后的真实模型回归

本机 `qwen3.5:9b` 复跑发现，拜仁场景在用户确认中锋后得到 0 个候选，LangGraph 仍把下一步交给模型；模型再次以 `offset: 10` 查询空结果并重复提出不合适的问题，最终触发策略循环保护。根因是已记录的 `confirmedPositionSearchMatchCount === 0` 没有对应的确定性分支。

已修复：空结果现在先询问是否扩大位置范围；用户保留原位置时直接完成并如实说明无样本；用户同意扩大到其他前锋位置时，`ATT` 位置族约束会覆盖检索、评估、证据审核与推荐。拒绝扩大位置的回答不再被解析成同意扩大。

快速回归：新增同案追问测试覆盖询问、拒绝后结束，以及扩大至其他前锋位置并推荐匹配位置族球员。`node --import tsx --test tests/*.test.ts` 104/104 通过；API 和网页 TypeScript 检查、网页生产构建通过。

修复后的本机 Ollama 全量运行：`barcelona-under-23-midfielder` 61.7 秒，全部硬性检查通过；`bayern-kane-replacement` 32.0 秒，全部硬性检查通过，角色确认后中锋搜索从 offset 0 返回空，再停在清晰的范围选择问题。每场景一次只验证本次运行的行为，不证明长期稳定性、推荐准确率或真实球员数据质量。

### 2026-10-04 — 进度回调和失败类别记录

本地模型 runner 会采集对话接口使用的 `onProgress` 回调，在 stderr 实时输出安全阶段事件，并将按 turn 编号的生命周期记录和阶段/状态计数写入 JSON 结果。失败摘要只写安全错误类别和可用状态码，不暴露原始异常文本。

### 2026-10-04 — 需求能力与推荐证据对齐

新增场景契约检查：评估器逐条查看推荐球员实际返回的 evidence key；如果该球员没有用户要求的能力指标，报告必须说明数据缺口；如果有可用指标，该推荐必须把对应指标列为重点依据。巴萨中场场景具体检查“推进”证据，并要求无法观测的“前场压迫”出现在数据限制中。安全 trace 也记录评估环节实际返回的指标 key，便于复核来源覆盖。这样能区分“引用了有效指标”和“指标确实回答了用户的问题”。

2026-10-04 复跑 `barcelona-under-23-midfielder`：Qwen 3.5 9B 用时 79.0 秒，20 条候选记录中系统评估 10 人，输出 1 名 MID 候选。推荐重点依据包含渐进传球成功率；“施压”无可用指标并在报告限制中披露。随后将检查收紧为逐条推荐核验，再跑一次相同场景，新增 `requestedCapabilitiesGrounded` 检查和全部场景硬性检查仍通过。两次单场通过验证链路行为，不验证推荐排序质量。

2026-10-04 新增 `progressMatchesObservedToolsAndTurnState`：本机模型 Harness 将同一 `onProgress` 回调与工具观察轨迹按实际阶段顺序对照，要求每个工具调用都有开始和结果事件，并要求 `needs_input`/`completed` 响应对应暂停/完成终态。该项验证 Agent trace、UI 进度 DTO 和最终状态之间的可观测一致性，不把事件数量当作质量分。

### 2026-10-05 — 真实模型分页循环与报告检索修复

把凯恩接班人 Harness 扩展为两次按需确认，并加入空中锋样本、用户同意扩到 ATT 后继续评估的检查。首次真实 `qwen3.5:9b` 运行暴露两个问题：报告检索完成后模型重复请求相同动作；新增评估批次会重新查询旧候选报告，报告工具预算也低于可评估批次数，最终命中循环保护和安全步数上限。

修复后 LangGraph 将评估与本批新球员的报告检索作为确定性策略阶段，并新增受约束的 `expand` / `reorient` / `conclude` 决策 schema。`expand` 只能请求准确 `nextOffset` 与原筛选条件；筛选耗尽后 `reorient` 仍允许模型换用户未限定的候选范围。报告查询仅覆盖尚未尝试的已评估球员；报告查询预算与最多三次评估批次对齐，单轮安全步数设为 16。

复验：本机 `qwen3.5:9b` 在 `curated` Wyscout 2017/18 数据上以 285.6 秒完成两次确认的同案调查，全部 18 项场景检查通过。Agent 先调查后询问角色；中锋搜索返回 0 后再次询问扩围；用户同意后按 ATT 从 offset 0、20、40 搜索，评估 30 人，并为每批新候选执行独立报告检索，最终返回 1 名 ATT 球员及 7 个实际证据键。工具 trace 和 64 条进度事件的阶段、轮次与终态检查全部通过。

确定性验证：全套 `pnpm test` 129/129 通过；`pnpm build`、`pnpm build:web` 通过。单次 285.6 秒通过只证明该次工作流行为正确，不证明长期稳定性、推荐排序准确性或历史样本代表当前市场。
