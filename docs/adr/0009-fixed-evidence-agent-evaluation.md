# ADR-0009: Evaluate real scouting workflows against fixed evidence

Status: accepted

Evaluate the actual compiled scouting graph, request understanding, identity resolution, source readers, and deterministic comparison/recommendation algorithms against versioned fixed evidence, using a real model through the configured gateway. A local TypeScript evaluation driver runs outside the production graph, with isolated trials and scripted multi-turn/interrupt interactions; small SQLite snapshots and recorded API-Football responses control source drift while preserving actual application behavior. Source facts and golden arithmetic/order are established independently of the evaluated version's output.

Combine deterministic behavior/evidence checks with one independently configured, calibrated semantic judge. Distinguish factual contradictions, unsupported factual additions, and false scouting execution claims; actual attempts, parsed business outcomes, and saved-result reuse establish execution evidence. Assign one most-specific category to each claim: process claims are execution errors, directly disproved facts are contradictions, and unsupported facts are claims that are neither supported nor contradicted. Different claims in one response may produce different categories. A confirmed critical violation fails the trial, while uncertainty, missing adjudication, and infrastructure failures remain visible. Automated review is recorded as automated review, and recommendation results establish compliance with fixed FM rules and evidence rather than independent real-world scouting relevance.

Deterministic identity checks ignore Unicode diacritics in mention strings so equivalent spellings such as “Krstovic” and “Krstović” do not fail on typography alone. They still require exact selected candidate IDs, canonical Reep IDs, provider source IDs, and resolution statuses. This comparison rule does not change runtime identity resolution.

Start with 48 cases split into 32 development and 16 held-out cases, plus 32 separate judge anchors split equally into development and validation. Formal reports retain three state-isolated trials per case; these are repeated executions rather than three independently sampled questions, and all reserved judge anchors must pass before semantic scores are valid. Keep real extracts and reports local, explicitly cap all physical model requests, run real-model evaluations manually, and use routine CI for offline validation. Establish the development baseline before choosing aggregate thresholds and freezing a version for held-out evaluation. The accepted scope and delivery sequence are recorded in [the evaluation plan](../../.scratch/agent-evaluation/plan.md).
